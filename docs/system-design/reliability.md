# Отказоустойчивость и восстановление

Статус всех чисел ниже: **целевые критерии приёмки**, не гарантии текущей поставки.
Область HA: отказ одного процесса или одного независимого узла. Потеря площадки,
внешнего интернета или всего кампусного Wi-Fi рассматривается отдельно.

## Целевые показатели

| Показатель | Цель и граница |
|---|---|
| Доступность команд занятия | 99,9% за месяц, считать по успешным валидным попыткам пользователей |
| Смена слайда → получение control state | p95 ≤ 1 с, p99 ≤ 2 с при исправной инфраструктуре и оговорённой сети |
| Принятая бизнес-команда | p95 ≤ 300 мс, p99 ≤ 1 с без передачи файла/видео; overload учитывать отдельно |
| Потеря одного gateway/API | Обнаружение и восстановление обслуживаемых клиентов ≤ 30 с, p95; без создания новых участников |
| Failover PostgreSQL | RTO ≤ 60 с; RPO 0 для подтверждённых транзакций при одном отказе и корректном sync/fencing |
| Потеря SFU-узла | Восстановление видео пострадавших комнат p95 ≤ 30 с; слайды/команды доступны независимо |
| Отчёт завершённого занятия | p95 готовности ≤ 60 с, при отставании показывать статус и watermark |
| Потеря всей площадки | Предварительная DR-цель RPO ≤ 5 мин, RTO ≤ 4 ч; требует независимой копии, площадки и restore drill |

Нормальные latency SLO не распространяются на период объявленного отказа: для него
есть отдельный RTO. Команда с 429/503 не считается успешно обслуженной. Завершение
доставки SSE не доказывает внимание студента и не заменяет текущую модель присутствия.

## Поведение при сбоях

| Сбой | Что продолжает работать | Восстановление и проверка |
|---|---|---|
| API process/host | Другие реплики; уже открытый media stream | LB снимает readiness; повтор только с прежним idempotency key; проверка отсутствия дублей |
| Gateway | Другие подключения и команды | Reconnect с jitter на любую реплику, новая проверка прав и snapshot; комнатные leases не принадлежат gateway |
| SFU process/host | HTTP-команды, вопросы, голосования, слайды | Повторная публикация/подписка пострадавших комнат; reserve N+1; это разрыв видео, не бесшовная миграция |
| TURN узел | Прямые WebRTC-подключения и другой TURN | Проверять настоящий relay traffic; surviving TURN не должен стать узким местом |
| Media Access Agent | Другие SFU-узлы и бизнес-команды | Supervisor останавливает связанную SFU-инстанцию, чтобы expiry прав не зависел от зависшего agent |
| PostgreSQL primary | Уже загруженные материалы и часть media delivery | Только eligible synchronous standby становится primary; команды ограниченно ждут, затем понятный временный отказ |
| Потеря DB quorum/нужной sync replica | Чтение уже разрешённого локального материала | Записи закрываются по deadline, не подтверждаются «в память»; не продвигать отставший узел ради зелёного health |
| RabbitMQ node | Quorum очередей 2/3 | Confirm/ACK, повтор eventId и inbox; не считать transient gateway queue долговременным журналом |
| Весь broker | Команды до установленного бюджета outbox; медиа | Gateway временно сверяет состояние пакетно по комнатам; рост outbox ограничен и виден оператору |
| Consumer | Команды и другие consumers | Lease истекает, задача возвращается; старый fencing token не может завершить новую попытку |
| Redis cache/quota | Уже подтверждённые записи PostgreSQL | Ограниченный локальный admission, cache rehydrate; не хранить там единственную копию голосов |
| Media Redis | Бизнес-команды | Отдельно тестировать сигналинг/существующие потоки/новые комнаты; не обещать непрерывное видео при любом Redis outage |
| Converter/тяжёлый файл | Идущие занятия с готовой колодой | Лимиты CPU/RAM/PID/времени и durable retry; пользователь видит задержку импорта |
| Object storage node | Объекты при допустимом failure budget хранилища | Проверка версии/checksum; не считать один NFS-сервер отказоустойчивым storage |
| MAX недоступен | Обычный веб при доступном origin | Provider cooldown, очередь/DLQ; не повторять storm на каждое сообщение |
| Диск заполнен | Зарезервированный путь control-команд до safe threshold | Сначала остановить импорт/экспорт и публикацию больших файлов; при угрозе WAL не ACK новые записи |
| Сеть разделила узлы | Кворумная сторона | Minority не становится вторым primary; истёкшие access leases закрывают приватную доставку |
| Ingress/LB узел | Второй независимый вход | Стабильный адрес площадки переключается; TCP может оборваться, клиент восстанавливается с прежней личностью |
| Весь хост/питание кампуса | Только то, что есть на независимой площадке | DR runbook; UPS или restart policy не равны полноценному резервированию |

## База и split brain

Предлагаемый базовый контур: PostgreSQL primary + 2 standby на независимых узлах,
Patroni, DCS quorum из 3 участников, стабильный write endpoint и проверенное fencing.
`synchronous_mode` вместе с `synchronous_mode_strict`, `synchronous_commit=on` и
правилом выбора допустимой replica должны быть согласованы. При отсутствии
необходимой синхронной копии доступность записей уступает сохранности.
Это поведение описано в [Patroni replication modes](https://patroni.readthedocs.io/en/latest/replication_modes.html).

Старый primary обязан потерять возможность принимать запись до продвижения нового.
Проверяются lease/DCS timeout, watchdog/STONITH выбранной площадки и защита от
paused VM. Резервные процессы на одном гипервизоре не независимы.
Основание: [Patroni watchdog](https://patroni.readthedocs.io/en/latest/watchdog.html).

RPO 0 в этом контуре относится к подтверждённым commit и одному отказу, а не к
одновременной потере всех актуальных копий. Timeout клиента не равен rollback:
после reconnect нужна проверка результата. Не включать автоматическое продвижение
заведомо отставшей replica без явного признания возможной потери данных.

Пулы всех API/workers учитываются совместно, включая максимум HPA, миграции и
backup. Gateway не имеет JDBC pool. PgBouncer transaction pooling не включается
вслепую: текущие advisory locks и backup-сессии требуют отдельной проверки;
session locks нельзя переносить между чужими server connections.

## Брокер, cache и storage

RabbitMQ: 3 независимых узла, quorum queue с majority, publisher confirm и manual
ACK. Quorum теряет доступность при потере большинства; это не причина переходить
на небезопасный single-copy режим. Диск, память, queue lag и outbox high watermarks
имеют alarm до исчерпания ресурсов.

Redis Sentinel использует асинхронную репликацию: при failover возможна потеря
недавно подтверждённых Redis-записей. Поэтому в Redis находятся cache, временные
квоты и media coordination, но не единственные бизнес-факты.
[Документация Sentinel](https://redis.io/docs/latest/management/sentinel/).

Object storage должен иметь versioning, проверку checksum, несколько fault domains
и независимую backup-копию. Совместимость с S3 сама по себе не означает HA. Сначала
выбрать существующую площадку учреждения и её гарантии; конкретный storage product
и число дисков определить до закупки/production deployment.

## Выпуски и обслуживание

- Readiness отвечает, можно ли обслужить данный вид трафика; liveness не перезапускает
  все API только потому, что временно недоступен PostgreSQL или broker.
- Убирать gateway из новых подключений, дренировать/переподключать ограниченную
  долю клиентов. Нельзя одновременно оборвать 10 000 SSE при rolling update.
- SFU draining оставляет активные комнаты; плановое обновление ждёт окончания
  занятий или согласованного окна, а не подменяется коротким `terminationGracePeriod`.
- Anti-affinity и запас CPU/RAM/NIC проверяются после потери узла. PDB регулирует
  добровольные disruptions и не предотвращает аварийный отказ физического узла.
  [Документация PDB](https://kubernetes.io/docs/tasks/run-application/configure-pdb/).
- Одна migration job на владельца БД; expand/migrate/contract, совместимые N/N-1
  контракты. Удаление столбца или event field не входит в обычный rolling release.
- Откат бинарника разрешён только при совместимой схеме. Restore старой БД поверх
  новых пользовательских записей не является автоматическим rollback.

## Резервные копии и DR

Для PostgreSQL: base backup + непрерывный WAL archive в независимом хранилище,
шифрование и проверка восстановления до заданного времени. Для blobs: immutable
версии и manifest ссылок, совместимый с DB recovery point. Межсервисные проекции
восстанавливаются по каждому владельцу, затем сверяются watermark и backlog.

Текущую согласованную пару DB/blob сохранять до окончания перехода. Перенос в
object storage требует новой процедуры восстановления, а не переименования tar.
Первый restore drill проводится в изолированной сети, без отправки реальных
webhook/сообщений пользователям. После восстановления повторно проверить роли,
анонимность, принятые голоса, материалы и отсутствие двойных внешних доставок.

Минимум раз в квартал и после существенного изменения хранения: восстановить копию,
измерить фактические RPO/RTO и сохранить протокол. До успешного drill числа из этой
страницы остаются целью. Нельзя утверждать автоматическую HA/DR только по YAML.
