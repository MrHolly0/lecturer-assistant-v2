# Автоматическое масштабирование установки

Реализовано в `feature/scalable-architecture`. Один вуз получает одну установку;
число экземпляров внутри неё меняется по нагрузке. 10 ноября 2026 проверен настоящий
KEDA/HPA в Linux-контейнерах на Mac: 120 синтетических студентов, рост Gateway
2 → 4, приём подключений новыми копиями, уменьшение 4 → 2, восстановление SSE
без повторного join. Это функциональная проверка контроллера, не новая нагрузочная
приёмка 10 000 и не проверка отказа физических серверов.

## Правила

| Компонент | Сигнал | Нижняя / верхняя граница по умолчанию |
|---|---|---|
| Application API | CPU, цель 65% от request 500m | 2 / 6 |
| Realtime Gateway | Сумма активных SSE и WS, 2 500 на копию | 3 / 6 |
| Content Worker | Готовые и выполняемые/оставленные import jobs, 2 на копию | 2 / 4 |
| Converter | CPU, цель 65% от request 500m | 2 / 4 |
| Analytics | Готовые и выполняемые report jobs, 8 на копию | 2 / 4 |

CPU обслуживает штатный Kubernetes HPA; для метрик соединений и PostgreSQL-очередей
используется KEDA 2.21.0. Только CPU недостаточно для Gateway: множество открытых
соединений может почти не расходовать процессор. Durable очередь задач находится
в PostgreSQL, поэтому считается там, а не по числу RabbitMQ invalidations.
Scale-to-zero не используется: у интерактивного занятия остаются готовые копии.
[HPA](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/),
[Prometheus scaler](https://keda.sh/docs/2.21/scalers/prometheus/),
[PostgreSQL scaler](https://keda.sh/docs/2.21/scalers/postgresql/).

Рост ограничен HPA-политикой 2 копии за 30 секунд; снижение использует окно
стабилизации 300 секунд и политику Pods=1/60s. Стандартный HPA учитывает историю
рекомендаций и изменений, поэтому это не отдельный жёсткий таймер. Нужны время
измерения, решение контроллера и запуск. Пороги подбираются по замерам площадки.

Пропажа Prometheus/неуспешный scrape не превращается в нулевую нагрузку.
После трёх ошибок KEDA включает ограниченный максимум. Это расходует резерв,
зато не уменьшает кластер из-за сломанной телеметрии. Такая же fallback-политика
задана для SQL scalers. Для CPU действуют стандартные правила HPA без этого
fallback. При отказе самого KEDA/control plane новые решения недоступны,
работающие копии продолжают обслуживание; нужны мониторинг и ручное управление.

## Завершение лишней копии

SIGTERM сразу закрывает admission/readiness. Существующие соединения уходят в
случайные моменты в пределах 20 секунд (`DRAIN_WINDOW_MS`, допустимо 0..30000).
До закрытия продолжаются продление прав, invalidations и доставка. Истёкший grant
по-прежнему запрещает приватные кадры. Новые подключения в уходящую копию получают
503/Retry-After. WS закрывается кодом 1012, временная недоступность grant — 1013;
1008 остаётся для отказа в доступе/неверного scope. Через окно + 5 секунд остаточные
sockets закрываются принудительно; Kubernetes даёт 45 секунд до kill.

Открытое TCP-соединение не переносится между процессами. Новые соединения идут
в новые ready-копии, при уменьшении старые переподключаются с существующим токеном.
После роста уже открытые соединения остаются на прежних копиях: принудительное
выравнивание их числа между Gateway не реализовано. Поэтому минимум/порог/запас
должны выдерживать скачок нагрузки до подключения новых копий.
Gateway не создаёт участника повторно. Краткое переподключение возможно;
актуальное состояние восстанавливается из Application. Это не обещание доставки
каждого промежуточного кадра при отключении.

## Включение на площадке

1. Подготовить кластер/данные/сеть/secrets по `deploy/scalable/README.md`.
   Установить совместимые metrics-server, KEDA и Prometheus. В тесте использованы
   K3s 1.35.5, KEDA 2.21.0, Prometheus 3.16.0; проверить официальные release digest.
2. Добавить объект из `deploy/scalable/ha/autoscaling.example.json` под ключом
   `autoscaling` в release JSON. `prometheusAddress` доступен из KEDA и отдаёт один
   набор серий job=realtime для namespace установки. Для HA Prometheus нужна
   дедупликация: простое суммирование его реплик удвоит наблюдаемую нагрузку.
3. `python3 deploy/scalable/ha/render.py release.json --prometheus-config`
   выводит scrape config. Включить его job в свой Prometheus. ServiceAccount
   сборщика нужны get/list/watch pods только в namespace установки. Scrape идёт
   на pod:8091/metrics; notReady-поды не исключаются, пока дренируют соединения.
   Метрики и Prometheus не публикуются наружу.
4. Создать отдельные LOGIN `content_scaler` и `analytics_scaler` с приватными
   паролями в соответствующих БД. Выполнить `ha/scaling-content.sql` и
   `ha/scaling-analytics.sql` владельцами таблиц. Разрешены только столбцы очереди,
   чтение, timeout=2s и четыре соединения на роль.
5. Создать Secrets `lecturer-scaling-content` и `lecturer-scaling-analytics`, ключ
   `connection`: PostgreSQL connection URL каждой роли. Пароли URL-encoded; для
   межузлового соединения использовать TLS/проверку CA, например
   `sslmode=verify-full`, и доставить CA контроллеру. Не записывать URL с паролем
   в release JSON, Git, shell history или открытый журнал.
6. Renderer проверяет бюджет БД до выпуска manifests: API имеет два pool (12+4),
   Content — 4 на worker, ещё 30 зарезервированы. По умолчанию максимум требует
   142 из 180 подключений основной БД. Для отдельной Analytics БД — 4×4+20=36
   из бюджета 60. Бюджеты должны соответствовать настройкам БД и включать
   служебные соединения, rolling-update surge и запас администратора.
7. Применить CRD/secrets/scrape, затем release manifests. HPA владеет replicas
   пяти масштабируемых Deployment: renderer не пишет этот атрибут при включённом
   autoscaling. При переходе со старого client-side apply отдельно передать
   владение полем контроллеру, не сбрасывая число копий: сначала включить HPA
   и проверить минимум, затем убрать старое владение. Проверить Ready у
   ScaledObject, targets у HPA, метрики и свободные ресурсы.

PostgreSQL, RabbitMQ, Redis и SFU по этим политикам не масштабируются. Дополнительным
pod нужны свободные CPU/RAM узлов. Когда их не хватает, администратор добавляет
Linux-сервер в кластер; автоматическое создание машин не реализовано. Новые
media-узлы добавляются отдельно с расчётом сети и drain комнат. У БД свои
replica/failover/backup правила; рост API ограничен бюджетом её соединений.

Локальные квоты API также получают фиксированные доли от бюджета установки,
делённого на coreMax+1 (запас rolling update). Например, reads=7200 и writes=1440
на subject в минуту распределяются между максимумом копий; общий concurrency
бюджет — 768 запросов, из них 48 дорогих чтений. Все бюджеты приведены в
`ha/autoscaling.py:RATE_BUDGETS`, переопределяются `autoscaling.rateBudgets`.
При двух копиях часть квоты не используется. Это защита от умножения локальных
лимитов при scale-up, не общий sliding-window counter: рестарты сбрасывают
локальную историю. Строгая глобальная квота и полный нагрузочный цикл API HPA
этой функциональной проверкой не подтверждены.

## Проверка на Mac

Протокол: `verification-20261110-autoscaling.json`. Docker: 8 CPU, 8 321 994 752
байта RAM; два K3s-узла разделяют одну VM. Настоящие API/БД/RabbitMQ находятся в
изолированном Compose, Gateway/Prometheus/KEDA — в Kubernetes в той же закрытой сети.
Лабораторные пороги: 20 соединений/копию, 2..4 копии, окно снижения 30 секунд,
drain 6 секунд. Production-пороги проверены renderer-тестами, а не нагрузкой этого
малого прогона.

- 120 студентов получили snapshots; все четыре Gateway принимали подключения.
- После сохранения 30 клиентов контроллер вернулся к двум Gateway; пять активных
  SSE переподключились, получили новую версию, осталось ровно 120 участников.
- Приватный AUTHOR-ответ получил автор, остальные 119 его не получили.
- При выключенном Prometheus контроллер поднял bounded fallback до четырёх копий,
  доставка продолжилась. Prometheus затем возвращён.
- SQL обеих очередей выполнен на настоящих БД под ограниченными временными ролями;
  записи запрещены, роли откатили. Это проверка SQL/прав, не нагрузочный цикл
  autoscaling всех фоновых работников.
- 24 unit-теста сервисов и 7 renderer-тестов прошли, включая admission race при
  SIGTERM, drain с действующими правами и отклонение чрезмерного DB budget.

Для повторения на подготовленной лаборатории `deploy/scalable/autoscale-lab.py`
создаёт private manifests (0600) только из её `.env` и Docker IPs. Применять
исключительно с `/private/tmp/lecturer-autoscale.kubeconfig`.
`SCALE_LAB=true node e2e/autoscaling.mjs` проверяет настоящий controller loop;
Gateway руками не масштабируется. Порты API/SSE: loopback 18089/18091.
Старый стенд, MAX, туннель и глобальный kube context не используются.

Не подтверждены независимая HA/RPO/RTO, автоматическое добавление серверов,
10 000 видеозрителей и production sizing. Отдельная массовая проверка управляющего
контура описана в `implementation.md` и не заменяет эти испытания.
