# Реализация распределённого профиля

Ветка `feature/scalable-architecture`, база `a404fa5`. Обычный режим приложения
сохранён; новая конфигурация включается отдельно. Инструкции и параметры:
[deploy/scalable](../../deploy/scalable/README.md).

Автоматическое масштабирование HPA/KEDA, budgets и отдельная функциональная
проверка 2 → 4 → 2 Gateway на Mac описаны в [autoscaling.md](autoscaling.md).
Это дополнение не меняет границ приёмки массового видео и независимой HA.

## Доработка восстановления 10.11.2026

Истечение пятисекундного разрешения приостанавливает защищённую доставку и
удаляет несброшенный буфер. Соединение может дождаться новой проверки прав в
течение 30 секунд от исходного expiry. Новое разрешение возвращает свежий снимок;
deny закрывает соединение сразу, а ошибки и задержанные ответы не продлевают
окно ожидания. TTL доступа остался прежним. Продление планируется от фактического
deadline; повторные ошибки имеют backoff/jitter до 2 секунд на комнату.

Сквозной fault test останавливает все три Gateway на 8 секунд, меняет слайд и
исключает студента. Затем отдельно останавливает оба Application на 8 секунд.
Разрешённые SSE/пульт восстанавливаются по прежним соединениям; исключённый
студент не получает новых кадров. Во время потери authority метрика подтверждает
приостановку доставки студентов и ведущего. Это отдельная проверка восстановления,
не результат healthy latency под нагрузкой 10 000.

Сервисы используют проверенный Node.js 24 LTS с закреплённым digest образа.
Выбор после сравнения с Go/Bun/NATS описан в [technology-review.md](technology-review.md).
Добавлены агрегированные CPU/GC/event-loop метрики, cgroup/pressure и DB wait
collectors, а также Linux runner с ограничением ресурсов и строгим readiness gate.
Чувствительные заголовки удаляются из runtime-журналов внутреннего прокси.

## Подтверждённый управляющий прогон

Впервые прошли **оба полных синтетических прогона на 10 000 студентов**:
обычная конфигурация и работа на оставшихся репликах после отключения одного
Application, одного Gateway и одного RabbitMQ. Результаты и точная среда:
[verification-20261110-recovery.json](verification-20261110-recovery.json).

| Проверка | Обычная конфигурация | По одной реплике API/Gateway/RabbitMQ отключено |
|---|---:|---:|
| Занятия / студенты | 100 / 10 000 | 100 / 10 000 |
| Подключение / повторное подключение | 10 000 / 10 000 | 10 000 / 10 000 |
| Принятые голоса / отклонённые дубли | 10 000 / 10 000 | 10 000 / 10 000 |
| PNG | 50 000 | 50 000 |
| Ошибки потока / приватности | 0 / 0 | 0 / 0 |
| p95 доставки слайдов | 1,58–1,71 с | 1,54–1,77 с |

Завершение тестовых занятий, проверки соседних занятий и HTTP fallback также
прошли. Ограниченные 429/503 и повторы остаются в протоколе. Генератор использует
отдельный ограниченный HTTP pool для команд/PNG: массовое закрытие SSE больше
не делит с ними неограниченный пул соединений. Неудачный предыдущий прогон с
ошибками cleanup сохранён, после исправления выполнен новый полный прогон.

Среда — Docker Desktop, 8 vCPU и около 8 ГБ VM, Linux-генератор с лимитом 2 CPU /
1 ГБ в той же сети. Это одна машина. Физическое разделение узлов, холодные разные
колоды, шестичасовой mixed soak и 10 000 голосов за 5 секунд здесь не проверялись.
Отказ реплик введён **до** начала нагрузки; это не измерение RTO миграции уже
подключённых клиентов при внезапной потере хоста.

Отдельно 16 headless Chromium-клиентов получили и показали каждый по 73 кадра
1280×720 за 5 секунд, без packet loss в замере. Фактический поток малоподвижной
сцены около 130 Кбит/с на зрителя. Это проверка настоящего кодирования/декодирования,
а не массового видео 6 Мбит/с. Все тестовые браузеры и временный harness закрыты.

## Выполнено в коде

| Часть | Реализация и граница |
|---|---|
| Application | Две реплики в лаборатории; бизнес-команды и outbox в одной транзакции PostgreSQL. Отдельный read-only pool для проверок прав защищает продление от занятых write connections. Существующие права, idempotency, moderation и presence сохранены |
| Integration | V47/V50, ограниченный outbox, SKIP LOCKED claims, fencing, broker confirms, backoff/jitter, DEAD/redrive, короткая отложенная очистка квот |
| Realtime | Независимые Node Gateway: прежний SSE и scoped STOMP wire format, ephemeral Rabbit queues, coalescing, ограниченные буферы, приватные overlays и пакетное продление прав |
| Content | Отдельный Java entrypoint без IAM/live компонентов, ограниченная роль БД, существующие durable jobs/lease/fencing и converter. Метаданные/API Content ещё принадлежат Application |
| Analytics | Node consumers/workers, отдельная PostgreSQL, inbox dedupe, fenced generation, versioned reports и read repair. Источник отчёта — согласованный export Application |
| Media | LiveKit SFU, Media Control, короткие publisher/subscriber tickets, durable room/grant metadata в Application. Видео не передаётся через HTTP API |
| Media access | Локальный inventory и supervisor на каждом SFU; проверка действующих участников, принудительное удаление и прекращение потока при истёкшем разрешении |
| Web | Выбор провайдера по capability API, публикация/приём SFU, lazy SDK, ограниченный resync больших снимков без блокирования здорового транспорта |
| Вход студентов | Новым гостям и MAX-профилям без пароля не вычисляется bcrypt случайного неиспользуемого пароля; парольный вход им запрещён. Пароли обычных аккаунтов сохраняют прежнюю защиту |
| Эксплуатация | Изолированный Compose, три RabbitMQ узла, reference Kubernetes renderer/CNPG/quorum, PDB/readiness/drain, метрики и инструкции восстановления |

Внешние команды остаются HTTP. Gateway не пишет в БД и не принимает команды по WS.
Он получает свежие разрешения до 5 секунд, обновляет их примерно каждые 2 секунды
и прекращает приватную доставку при недоступности authority после expiry. Lease
не продлевается из кэша. Deadline отсчитывается монотонно от начала RPC по интервалу
`checkedAt`→`expiresAt`, с вычетом задержки и запаса. Сдвиг wall clock не продлевает
старый доступ и не мешает получить новое разрешение после восстановления связи.

Общий снимок не содержит частных ответов. Индивидуальная часть собирается только
для разрешённых subjects, пачки Gateway ограничены 128 адресатами. Крупный снимок
заменяется небольшим invalidate, браузер выполняет один ограниченный HTTP-resync.
Потерянные transient события восстанавливаются комнатной сверкой через 15 секунд;
это режим деградации, а не обычная задержка доставки.

Фактический broker protocol v1 описан [JSON Schema](../../services/contracts/integration-event.schema.json).
Audience всегда INTERNAL. Consumer не рассчитывает суммы повторным добавлением
событий: событие инвалидирует отчёт, новый согласованный export заменяет проекцию.
Поэтому повтор/переупорядочивание не дублирует голоса и не откатывает готовый отчёт.

## Проверки

Синтетическая лаборатория использует другой Compose project, БД, volumes и порт
18089. Данные прежнего стенда и реальные привязки MAX не участвовали.

- 396 Java-тестов без ошибок, включая защиту passwordless-профилей и продление
  прав при полностью занятом основном DB pool; проверки
  форматирования/Checkstyle. Проверены права внутренних API, размеры снимков,
  outbox fencing/retry и SFU-grants/idempotency.
  Это проверки первоначального выделения; Java/web в доработке восстановления
  не менялись. Повторены 21 unit + 1 PostgreSQL-тест сервисов, 2 socket-pool
  integration tests и 3 теста HA renderer.
- 141 веб-тест, lint/format/build, 28 тестов MAX на локальных подставных серверах.
  21 unit-тест Node проверяет 6 000 соединений в одном
  hub, приватность, expiry, slow consumer, события во время refresh, STOMP scopes,
  publisher confirm, media permissions, watchdog, clock skew и задержанные grants.
- Реальная PostgreSQL: inbox dedupe, потеря lease, fencing старого worker,
  generation, точный fingerprint и безопасное отклонение неверного envelope.
- Сборка SFU запускает Go-тесты loopback inventory; три теста HA renderer и восемь
  тестов арифметики capacity model. Все application-образы собраны.
- Сквозной smoke: реальный PDF импортирован отдельным worker; SSE и STOMP получили
  изменение за 273 мс в последнем smoke; приватный ответ виден автору и отсутствует у другого студента
  и публичного снимка; publisher/subscriber права различаются; internal API закрыт
  снаружи; завершённый итог прочитан из отдельной Analytics DB.
- 10 занятий / 1 000 студентов: 1 000 SSE и reconnect, 5 000 PNG, 1 000 принятых
  голосов и 1 000 отклонённых дублей, 0 privacy/stream errors. Доставка слайдов
  p95 235–364 мс, PNG p95 25 мс в последнем прогоне, 0 stream errors. Это
  управляющий контур без видеонагрузки.
- Проверен smoke при остановленных одном Gateway и одном RabbitMQ узле. После
  полного выключения кластера исправлен порядок старта всех RabbitMQ участников;
  outbox backlog доставился после восстановления.

Браузер принимал настоящее SFU-видео 1280×720, в том числе внутри страницы
студента. При остановке обоих Application API новые кадры прекратились не позднее
10 секунд от начала аварийной проверки; ещё 39 секунд счётчик оставался неизменным.
Отдельная проверка подтвердила, что локальный supervisor остановил сам SFU.
Это проверка закрытия доступа, а не доказательство бесшовного восстановления видео.

Raw отчёты сохраняются локально в `artifacts/scalable-capacity-*`, снимки браузера —
`output/playwright/`; credentials в отчёты не включаются. Компактный переносимый
протокол: [verification-20261110.json](verification-20261110.json).

Прогоны 100×100 обнаружили OOM публичного Caddy при 256 МиБ и 1 ГиБ. После этого
публичный edge переведён на Nginx: неблокирующая передача SSE/WS, buffering off,
ограниченные соединения и 512 МиБ. Внутренний Caddy обслуживает только короткие
RPC. Исходные неудачные прогоны сохранены и не считаются успешно пройденными.

## Что осталось до полной приёмки 10 000

**Управляющий сценарий 10 000 прошёл; общая цель с массовым видео и HA не принята.**
История до доработки: в одном из промежуточных
прогонов все 10 000 подключились и восстановились, были получены 50 000 PNG,
приняты 10 000 голосов и отклонены 10 000 дублей, приватность не нарушена. Однако
потоки закрывались при истечении разрешений. Последующие прогоны после изоляции
DB pool также не прошли требование непрерывной доставки.

Метрики зафиксировали паузы event loop 6–38 секунд и отдельный сдвиг wall clock
на 15 секунд в локальной Docker VM (4 ГБ). Исправлены расчёт срока разрешения,
пулы, admission и буферизация; причина самих длительных пауз не установлена.
Увеличение TTL для маскировки пауз не применялось. В итоговой конфигурации такие
паузы не наблюдались; одновременно изменились среда/генератор/runtime, поэтому
однозначная причина прежних пауз не доказана. Успех короткого управляющего
сценария не подтверждает все latency/RTO SLO из матрицы.

Следующий gate — повторяемый mixed/failure прогон на независимых Linux-узлах с
профилями CPU/GC/I/O, DB wait events и сетевыми метриками. Матрица и критерии:
[acceptance.md](acceptance.md). До его прохождения этот профиль не следует
переключать на рабочую установку с такой нагрузкой.

## Что ещё требует площадки или отдельного этапа

1. Многосерверная приёмка, 10 000 реальных видеозрителей, TURN/narrow network,
   шестичасовой mixed soak и RPO/RTO/restore drill. Однохостовая Docker VM не заменяет
   такую площадку. Сетевой расчёт — 75/150 Гбит/с с накладными расходами при
   6/12 Мбит/с на зрителя; реальный room packing и CPU требуют измерения.
2. HA storage и перенос файлов в object storage. Сейчас требуется общий RWX том,
   его отказоустойчивость не создаётся приложением.
3. Полное выделение Content metadata/API/DB и независимый расчёт аналитики из
   событий. Эти части первого выпуска сознательно сохраняют Application authority.
4. Production операторы, ingress/LB/TLS, HA Redis/Sentinel, firewall/mTLS, секреты,
   backup/PITR и обновление с совместимой схемой. Reference YAML ничего не применяет.
5. Реальный MAX/Safari/iOS и проектор в новом media mode. Проверка Chromium
   клиентов подтверждает WebRTC path, но не покрывает все устройства.

Новый runtime не включён на прежнем стенде. Автоподнятие и туннель прежнего стенда
не восстанавливались. Установка этой ветки в рабочую среду — отдельное переключение
после выбора инфраструктуры и проверки её ограничений.
