# Контракты, порядок и согласованность

Это целевые требования полного перехода. Первый выпуск использует более узкий
внутренний протокол v1: [JSON Schema](../../services/contracts/integration-event.schema.json)
и [реализация](implementation.md). Он не передаёт broker payload браузерам;
audience в нём всегда `INTERNAL`, sessionId nullable, изоляция учреждения задаётся
отдельными БД/сетью/vhost. Поля installationId/correlationId/causationId из примера
ниже в runtime v1 не вводились. Пример остаётся направлением развития контракта.

## Команды

- Команды отправляются HTTP; WS/SSE доставляют события, но не обходят права API.
- У изменяющей команды есть `operationId`, `Idempotency-Key`, нормализованный hash
  payload и deadline. Scope ключа: установка + действующий actor + операция.
- Результат и бизнес-эффект записываются в одной DB-транзакции. Точный повтор
  возвращает исходный результат, другой payload с тем же ключом получает 409.
- Проверка прав повторяется при повторе команды. Результат не воспроизводится
  от имени другого вошедшего аккаунта. Guest claim не снимает mute/ban.
- После потери HTTP-ответа нельзя заключать, что запись не произошла. Клиент
  сверяет состояние операции либо повторяет её с тем же ключом.
- `expectedVersion` защищает управление слайдом/рисунком; голос защищён естественным
  уникальным ключом. Не обновлять общую строку занятия на каждом присутствии.

Повторы: full jitter, например случайная задержка от 0 до `min(30s, 0.5s * 2^attempt)`.
Это параметры проекта, не универсальный интервал для всех операций. `Retry-After`
является нижней границей. Отдельный retry budget на логическую операцию, не более
одной автоматической retry-цепочки; нижний слой RPC не перемножает попытки верхнего.
Ошибки 400/401/403/409 не повторяются как сетевые. HTTP deadline не обещает отмену
уже начатой транзакции; сервер также имеет statement/lock timeout.

## Integration event

```json
{
  "eventId": "uuid",
  "type": "lesson.poll.closed",
  "schemaVersion": 1,
  "installationId": "uuid",
  "aggregate": {"type": "poll", "id": "uuid", "revision": 7},
  "occurredAt": "2026-11-09T09:00:00Z",
  "correlationId": "uuid",
  "causationId": "uuid",
  "audience": {"kind": "SESSION_PUBLIC", "sessionId": "uuid"},
  "data": {"pollId": "uuid", "status": "CLOSED"}
}
```

Это пример формы, не готовая схема всех событий. До первого выделения сервиса
нужны JSON Schema/AsyncAPI, fixtures и проверки совместимости producer/consumer.

- Audience имеет отдельные варианты `SESSION_PUBLIC`, `SESSION_STAFF`, `PERSON`,
  `INTERNAL`. Область задаёт сервер. Название Rabbit routing key не даёт права чтения.
- PERSON-событие содержит внутренний subject для маршрутизации; публичный payload
  не содержит его, чужих ответов, имён анонимных авторов или teacher notes.
- Полный размер integration event ограничить 64 КиБ. Для больших manifest/report
  использовать versioned reference + checksum; доступ к объекту защищён отдельно.
- UUIDv7 и `occurredAt` не являются порядком commit. `session.version` сейчас
  покрывает не все виды изменений, поэтому его нельзя молча объявить cursor всех
  голосов/QA. Нужны версии конкретного aggregate и версии готовых проекций.

## Outbox и inbox

Новая таблица integration outbox содержит event payload, routing/schema version,
created/published timestamps, attempts, nextAttemptAt, leaseOwner и fencing token.
Бизнес-транзакция добавляет событие, publisher получает пачку через SKIP LOCKED,
отправляет persistent message с publisher confirm и проверкой unroutable return.
Нельзя отметить опубликованным до confirm; потеря confirm допускает повтор.

Consumer выполняет вставку `(consumerName, generation, eventId)` в inbox и изменение
своей проекции в одной транзакции. ACK отправляется после commit. Повтор eventId
не увеличивает счётчик второй раз. Порядок доставки между publishers и после retry
не гарантируется: consumer сравнивает aggregate revision, при пробеле перечитывает
снимок или запрашивает replay; устаревшее событие не открывает закрытый poll.

Срок inbox не короче допустимого горизонта redelivery/replay. Полная перестройка
аналитики запускается в новой generation и публикуется атомарной сменой указателя,
а не повторным добавлением старых событий в текущие суммы.

Для бизнес-consumers использовать durable quorum queues с явным лимитом байтов,
manual ACK и bounded prefetch. При заполнении запрещён беззвучный drop-head важных
команд. DLQ имеет alarm, причину, число попыток и управляемый redrive. Внешняя
доставка MAX остаётся at least once даже при идемпотентности нашей БД.
Обоснование механизма: [RabbitMQ confirms](https://www.rabbitmq.com/docs/confirms),
[quorum queues](https://www.rabbitmq.com/docs/quorum-queues).

Realtime-инвалидации имеют другую семантику: короткоживущие очереди на реплику,
latest-state coalescing, восстановление через снимок. Нельзя ACK бизнес-событие
только потому, что сокет принял байты; это не подтверждение обработки клиентом.

## Проекции и CQRS

Нужен практический CQRS: командная модель занятия и отдельные read models для
публичного состояния, персональных overlays и отчётов. Полный event sourcing не
нужен для этого масштаба и не следует из наличия журнала событий.

Materializer объединяет агрегаты светофора/голосов на коротком окне, например
250 мс, сохраняя все принятые записи. Готовая public projection получает свою
монотонную revision и terminal marker. Лидер materializer для занятия имеет
lease/fencing; после рестарта revision не начинается с нуля. Пробел в stream cursor
означает запрос нового snapshot, а не ожидание потерянной промежуточной дельты.

До границы извлечения не полагаться на `analytics.events` как на полный архив
всех фактов: текущие payload недостаточны для произвольного восстановления всего
продукта. Миграция проекций начинается с согласованного snapshot/backfill,
watermark и нового versioned event stream. Итог занятия может публиковать
ссылку на versioned export; содержание и watermark фиксируются согласованно.

## Права и приватность при распределении

Application API остаётся авторитетом идентичности/курса. Межсервисные запросы
аутентифицируются workload identity/mTLS с отдельными scopes; одного общего
секрета для всех служб недостаточно. Публичный ingress не пропускает internal API.

Gateway проверяет permission на connect/subscribe и получает короткую lease
не длиннее 5 секунд. Обновления собираются batch-запросами, например до 1 000
subjects, а не 10 000 HTTP-вызовами. Отзыв доступа инвалидирует lease немедленно
при получении события. Потеря связи с authority после TTL закрывает защищённую
доставку; gateway не продолжает её бесконечно из кэша. Цель отзыва доступа:
до 5 секунд при потере invalidation, измеряется отдельным fault test.

Перед отправкой содержимого личного ответа нужна свежая проверка конкретного
адресата/участия, при недоступности authority доставка закрыта. Событие с текстом
не отправляется во все публичные подписки «для фильтрации браузером». Имена и
постоянные теги анонимных авторов не добавляются в public/staff DTO.

Короткий media token не обеспечивает сам по себе отзыв открытого WebRTC-сеанса:
нужны server-side removeParticipant/room shutdown при ban/end, reconciliation
действующих участников и ограниченная lease при partition управляющего контура.
Если SFU не может принудительно остановить чтение после истечения разрешения,
этот security gate считается непрошедшим, независимо от количества зрителей.

Предлагаемый способ реализации этого требования: Media Access Agent рядом с SFU.
Он получает batch-разрешения с абсолютным сроком, продлевает только по свежему
ответу authority и удаляет истёкших участников через локальный admin API SFU.
При недоступности локального API он останавливает обслуживающий SFU. Supervisor
запускает SFU и agent как связанную отказную единицу: падение/зависание agent
прекращает media delivery, а не оставляет бессрочный доступ. Отказ этой пары
восстанавливается как отказ одного SFU. Lease и supervisor grace имеют общий
измеряемый revoke budget; для медиа предварительная цель до 15 секунд.
Это дополнительный компонент интеграции, не свойство stock LiveKit. Первый выпуск
реализует его в `services/media-supervisor` и локальном расширении SFU; проверенные
сценарии и оставшиеся security/failure gates перечислены в implementation.md.

Gateway и Media Access Agent проверяют пересекающиеся subjects независимо.
Расчёт должен учитывать оба потока проверок. Повторно используемое разрешение
не получает новый TTL из кэша: срок привязан к исходной проверке. Нужны ограничение
clock skew и запас при сравнении сроков; после неизвестного clock state доставка
закрывается. Внутренние гранты не передаются браузеру как административные токены.

## Ограничения нагрузки

Локальный admission на каждой реплике действует всегда. Для первого HPA-профиля
выбраны фиксированные квоты репликам: renderer делит бюджет установки на
coreMax+1 (включая update surge). Рост числа API не снимает верхний предел;
при малом числе копий часть бюджета намеренно не используется. Арифметика и
соответствие переменных реальной конфигурации проверяются renderer-тестом.
Это не общий Redis sliding-window counter: локальные окна сбрасываются при
перезапуске и не обеспечивают точную глобальную поминутную квоту сквозь рестарты.
Частые rolling updates и распределённые всплески требуют отдельного испытания;
для строгой общей квоты нужен выделенный backend, отдельно от media Redis.
Пределы NAT/IP не заменяют actor/session квоты. Детали: autoscaling.md.
