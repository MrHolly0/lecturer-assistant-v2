# Проверка 10 000 пользователей и отказов

Эта матрица задаёт полную приёмку. На дату документа она **не выполнена полностью**.
Arithmetic tests калькулятора не заменяют end-to-end, media и fault tests.
Синтетический управляющий сценарий 10 000 и работа при заранее отключённых
репликах прошли; измерения и границы: [implementation.md](implementation.md).

## Среда и данные

- Зафиксировать SHA/digest всех сервисов, CPU/RAM/NIC/SSD, версии ПО, policy
  replication, queue budgets, storage и реальную схему независимых узлов.
- 100 занятий с разными колодами и курсами, разные группы/права/аккаунты. Проверять
  skew 50/200/500/1 000 зрителей, а не один общий файл и одну равномерную аудиторию.
- 10 000 уникальных студентов, дополнительные окна ведущих/пульты/проекторы,
  guest/profile/MAX identities; исключённые и отозванные аккаунты.
- Несколько генераторов нагрузки с запасом FD, портов, CPU и NIC. Измерить их
  собственную загрузку и потери: ограничение генератора не выдаётся за лимит продукта.
- Реальные ingress/TLS/storage routes и WebRTC/TURN. Нельзя проверять только core
  напрямую, а публиковать результат для полного пути пользователя.
- Видеопубликации: 100 настоящих encoded streams и 10 000 subscriptions; выбирать
  профили из модели. Mock signalling или отправка одного JPEG не заменяет видеотест.

## Нагрузочная матрица

| Сценарий | Критерий |
|---|---|
| 1k → 3k → 5k → 10k | Все запланированные клиенты включены в знаменатель, подтверждены приём и восстановление |
| 10k стабильных клиентов, idle | Нет SQL/history query на каждый idle socket каждую секунду; стабильные память и FD |
| Смена слайда/рисунок | p95/p99 с момента команды до фактического применения нужной версии клиентом |
| Массовый опрос | 10k ответов за 5 с, совпадение уникальных принятых ответов, повтор с тем же ключом |
| Совмещённый пик | Голосование + сигналы + вопросы + receipts из модели; конечный ответ каждому запросу |
| Cold PNG/cache | Разные изображения и версии; доступность material storage, не только HTTP 200 снимка |
| 10k видео при 6 Мбит/с | Bandwidth/CPU/pps/packet loss/jitter, декодируемые кадры, читаемость кода |
| Профиль 12 Мбит/с | Полоса/room placement/память на собственной подтверждённой конфигурации; не подменять разрешение молча |
| TURN | 30% и 100% relay; TCP/TLS fallback, ограниченные сети и корректный deny при истечении media permissions |
| MAX/мобильные клиенты | Отдельная выборка физических MAX/iOS/Android/Safari, SDK/lifecycle/восстановление; синтетические 10k не доказывают поведение WebView |
| Soak ≥ 6 часов | Нет постоянного роста RSS/heap/очередей/FD, нет накопления просроченных jobs/outbox |
| Перегрузка выше цели | Bounded memory и backlog, измеримые 429/503; приоритет end/slide над импортом, восстановление после снижения нагрузки |

Здоровые SLO и recovery SLO оцениваются отдельно. В denominator входят handshake
failures, не успевшие подключиться, retries и отказ admission. Отдельно приводить
offered load, committed unique operations, delivery success и latency, а не только
красивый p95 для оставшихся успешных запросов.

## Fault injection под полной нагрузкой

| Отказ | Что доказать |
|---|---|
| Убийство одной API реплики | Продолжение работы, ровно один эффект команды при потерянном ответе |
| Потеря одного gateway host | Переподключение на другой узел за recovery target без смены личности/дубля участия |
| Убийство любого SFU | Только его комнаты теряют видео; вместимость survivor nodes, повтор публикации/подписки, доступность слайдов |
| Потеря TURN | Переподключение реальных relay-клиентов и отсутствие перегрузки оставшегося relay |
| Падение/зависание Media Access Agent | Связанный SFU прекращает обслуживание, права не превращаются в бессрочные; соседние узлы восстанавливают разрешённые комнаты |
| Потеря ingress/LB узла | Вход остаётся доступен, reconnect и повтор команд не меняют личность и не дублируют эффект |
| PostgreSQL primary | Нет потери подтверждённых голосов, один новый writer, фактический RTO |
| Разделение сети / paused primary VM | Нет split brain; minority не принимает commit после потери lease |
| Потеря sync replicas | Понятный временный отказ, отсутствие ложного ACK и скрытого async downgrade |
| Убийство broker node и всего broker | Quorum при одном отказе, bounded outbox при общем, восстановление/replay без двойных эффектов |
| Redis cache/media outage | Нет потери DB-фактов; контролируемый quota fallback; документированные последствия для видео |
| Падение import worker | Повтор claim с новым fencing token; старый worker не публикует результат |
| Worker slow/hang и disk full | Нет истощения ресурсов API/БД, alarm, ограниченный retry/DLQ |
| MAX 429/5xx/timeouts | Общий cooldown, нет storm, обычный веб продолжает работу |
| Обновление N → N+1 | Постепенный drain, совместимые contracts/schema; откат совместимого бинарника |
| Полная потеря площадки | Изолированное восстановление DB+blob+watermarks из независимой копии, измеренные RPO/RTO |

После каждого отказа сверить конечное состояние и попытки всех клиентов. HTTP
timeout не считается гарантированно потерянным запросом: разрешить неопределённые
результаты через прежний idempotency key и server ledger.

## Обязательные security-проверки

Соседние курсы/занятия не получают чужие вопросы/ответы; анонимность сохраняется.
Приватное событие не попадает в public broker routing/кэш. Reconnect с другим
аккаунтом не использует старый permission/cursor. Ban/kick/disable проверяются
при потере revocation event и partition authority. Media revoke проверяется на
уже установленном потоке. Заглушение не обходится обычным reconnect/guest claim;
возможность создать новую независимую гостевую личность остаётся отдельной
продуктовой границей без проверки ФИО.

## Отчёт и решение о выпуске

Сохранить config, model, load scripts, полный список запланированных клиентов,
latency histograms, errors/retries, RSS/GC/FD, NIC/pps, DB locks/WAL, replica lag,
queue/outbox/inbox lag, recovery timeline и проверки данных. Метрики не содержат
токенов и идентификаторов студентов в labels.

Результат формулировать как «эта ревизия на этой конфигурации прошла такие
сценарии». Непройденный пункт явно остаётся ограничением. Отсутствие измерения
падения узла не позволяет назвать схему HA, а 10 000 SSE не доказывают 10 000 видео.
