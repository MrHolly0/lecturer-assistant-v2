## Границы системы

| Часть | Ответственность и хранилище |
|---|---|
| React + nginx | Кабинет, администрирование, пульт, студент и отдельное окно проектора. Авторитетное состояние приходит с сервера. |
| Caddy | Один origin для web, `/api`, `/ws`, webhook и health. На локальном стенде перед ним туннель Tuna. |
| IAM | `iam.persons`, приглашения, identities, JWT/refresh, подтверждения перепривязки MAX. |
| Organization | Курсы, курсные роли и учебные группы; отдельно — произвольные вложенные группы сотрудников и их руководители. |
| Content | Исходники и изображения в blob storage, задания импорта и колоды в PostgreSQL. Конвертация — отдельный Python/LibreOffice/Poppler процесс. |
| Live / interaction / feedback / QA | Серверное состояние занятия, опросы, сигналы на слайде, вопросы и ответы. PostgreSQL-транзакции. |
| Channel | Сохраняемая очередь доставки в MAX; адаптер подтверждает конкретную попытку. При сбое MAX мини-приложение продолжает получать состояние через HTTP/SSE. |
| Analytics | История событий и SQL-агрегаты. Неиспользуемая `analytics.outbox` больше не заполняется; прежние записи сохранены, V25 дополнительно архивирует их. |

Модули обращаются к чужим Java-пакетам через `api`; ArchUnit проверяет это в CI. Границы не являются отдельными БД: текущая поставка — модульный монолит. OpenAPI: [контракт](../openapi/lecturer-assistant-v2.yaml); TypeScript-типы генерируются из него.

## Люди, роли и группы

- Одна установка обслуживает одно учреждение. Следующему учреждению нужны отдельные база, blob storage, настройки и бот. Изоляция нескольких учреждений в общей БД пока не реализована.
- Группы сотрудников необязательны. Учреждение само называет их: школа может сделать «Начальная школа → Учителя», вуз — «Факультет → Кафедра».
- Системная роль определяет доступ к продукту. Руководитель группы управляет её поддеревом; это отдельное право, оно не превращает человека в администратора.
- При переносе сохраняется роль каждого сотрудника в группе. Перенос руководителя меняет область его управления и требует явного подтверждения. Перенос «Без группы» снимает право руководителя группы. Пакетный перенос атомарен: ошибка одного участника отменяет весь пакет.
- Учебные группы студентов и роли в конкретном курсе независимы от групп сотрудников. В занятии хранится снимок выбранных учебных групп.

## Вход, отзыв и смена аккаунта

Парольный вход и вход через подписанные MAX initData выдают JWT с `auth_version`. Каждый защищённый HTTP-запрос проверяет текущие статус/роль/версию в БД. При истечении access token сервер отвечает 401, браузер один раз обновляет сессию по httpOnly refresh cookie.

Смена пароля, системной роли или статуса увеличивает версию, отзывает refresh и неиспользованные коды привязки. Старые access/participant token перестают работать. Запись Person блокируется до ротации refresh, чтобы конкурентная смена прав не оставила новую cookie после отзыва. После смены пароля пользователь входит заново.

WebSocket разрешает только точный `/topic/session/<UUID>` для управляемого курса; wildcard и клиентские SEND запрещены. Отзыв аккаунта закрывает соединение после commit; срок действия и курсные права дополнительно проверяются раз в секунду. SSE аккаунта отсоединяется после commit; запрет курса — при следующем снимке, обычно в течение секунды. Физическое закрытие медленного TCP соединения ограничено idle timeout 10 секунд; оно не блокирует команду преподавателя.

Перепривязка MAX: signed initData + пароль **либо** одноразовый код → просмотр текущего/целевого профиля → отдельное подтверждение. Preview не меняет identity и не создаёт сессию. Подтверждение действует 2 минуты, одноразовое, связано с MAX id и версиями аккаунтов; изменение привязки/прав требует нового просмотра. История остаётся у исходных Person, автоматического слияния нет. Отвязать MAX можно в кабинете своего аккаунта.

Kick действует в одном занятии и допускает явное повторное подключение. Ban закрывает идентифицированному человеку доступ к курсу и занятиям, пока преподаватель не снимет его через `DELETE /courses/{courseId}/bans/{personId}`. Disabled закрывает аккаунт во всей установке. Открытый гостевой вход по коду не подтверждает личность: для ограничения по человеку используйте вход MAX/аккаунт, а не новый гостевой профиль.

## Согласованность занятия и приватность

- Переходы статуса, слайды и действия опроса сериализуются блокировкой строки занятия; для опроса порядок блокировок: session → poll. Завершённое занятие нельзя вернуть в LIVE/PAUSED конкурентной командой.
- Изменения состояния получают возрастающую `version`. WS уведомление отправляется после commit; rollback не создаёт уведомления. При восстановлении связи/фокусе ПК и пульт перечитывают серверный снимок и связанные данные, устаревшая версия игнорируется. Страховочная сверка — раз в 30 секунд при открытом WS, раз в 5 секунд без него.
- SSE собирает снимки пакетно по занятию. Для каждого клиента хранится только последний ожидающий снимок и ограниченная очередь ответов. Снимки, отправка и закрытие используют отдельные ограниченные пулы; медленный клиент отсоединяется.
- Обычный вопрос виден преподавателю с именем. У анонимного вопроса имя не отображается участникам/преподавателю, но связь с Person хранится в БД для технического обслуживания. Это не анонимность перед оператором базы.
- Ответ AUTHOR получает автор; SESSION — аудитория. До отправки студенту показана видимость. Его вопросы сохраняются на сервере и возвращаются только ему в `myQuestions`.
- Код/QR проектора даёт возможность видеть показываемый материал; не размещайте его публично для закрытой лекции. Уже скачанные изображения и отправленные в чат файлы удалённо отозвать нельзя.

## Импорт и доставка

После рестарта PENDING/RUNNING задания переводятся в видимое терминальное состояние с объяснением; повтор создаёт новое задание из сохранённого исходника. Переполненный executor помечает задание FAILED/QUEUE_FULL. Ошибка до первого слайда — FAILED, после нескольких — PARTIAL; частичная колода требует подтверждения перед созданием лекции. Не обещается автоматическое возобновление с произвольного байта.

В `channel.outbox` у каждой аренды есть `attemptToken`. ACK должен совпасть с каналом и текущей попыткой IN_FLIGHT; запоздалый ACK старой аренды не перезаписывает итог. MAX использует небольшие пакеты, ограниченные timeout/retry и подтверждение каждого сообщения. Доставка остаётся **at least once**: сбой после отправки в MAX, но до ACK, может дать повтор, если внешняя платформа не предоставляет idempotency key. DLQ разбирается оператором, не бесконечным повтором.

## Запуск, обновление и откат

1. Первый запуск и секреты: [README](../README.md), [эксплуатация стенда](../deploy/stand/README.md), [.env.example](../.env.example). Первый администратор создаётся только с отдельным `ADMIN_SETUP_TOKEN`; далее пользователей приглашают администраторы.
2. Перед обновлением сохраните согласованную пару БД+blob и конфигурацию отдельно от Git. Скрипты/restore drill: [backup runbook](../deploy/stand/README.md#пара-резервной-копии-и-проверка-свежести).
3. Обновляйте только выбранный Compose-проект. Перед новой миграцией сначала запускайте CI и проверяйте upgrade на отдельной базе. Не вызывайте `down -v` для рабочего проекта.
4. `APP_VERSION` и `APP_GIT_SHA` задаются полным SHA. Проверьте `/api/v1/system/info`, health, реальные вход/подготовку/занятие/студента и время последней полной копии. Зелёный health не доказывает работу доставки в MAX.
5. Для отката держите прежние образы и пару данных. Старые миграции не редактируются; возврат Git-ветки сам по себе не откатывает БД. Полный restore — только при остановленных сервисах в явно выбранную пустую цель.

Резервная пара блокирует запись/удаление blob на время `pg_dump` + архива файлов. Длительная конвертация заканчивается до захвата backup-lock. Публикация пары атомарна, контрольные суммы проверяются, lock снимается явно на сервере PostgreSQL. Назначение задаётся `BACKUP_DESTINATION`; копия на том же Mac защищает от удаления Docker volumes, но не от потери самого диска. Для эксплуатации нужен отдельный носитель/удалённое хранение и проверка его доступности.
