# Кадр демонстрации в личном чате MAX

Студент может запросить текущий кадр демонстрации как файл JPEG в своём личном чате
бота MAX. Вложения `file` используются вместо `image`: адаптер отправляет исходные
байты JPEG без дополнительного изменения размера или перекодирования.

## Запрос

`POST /api/v1/student/sessions/{joinCode}/screen-share/frame/chat`, без тела.
Для подключения используется `X-Participant-Token` или авторизованный аккаунт.
Если переданы оба удостоверения, они должны принадлежать одному человеку.

Перед постановкой в очередь сервер проверяет действующее участие и доступ к курсу,
а также работающую демонстрацию без паузы и свежий кадр возрастом менее четырёх
секунд. Один код занятия не даёт права запрашивать доставку. Запрос не подключает
человека к лекции заново и не создаёт WebRTC-подключение.

Получатель определяется только по привязанному MAX-профилю участника. В запросе
нет адреса назначения, URL изображения, номера слайда или загружаемых байтов.
Отсутствующая привязка MAX возвращает `409` с предложением открыть бота и связать
аккаунт. Ответ `202` означает постановку в outbox, а не подтверждение доставки MAX.
Другой кадр можно запросить через десять секунд; повтор того же кадра идемпотентен.

В подписи указаны дата и время получения кадра сервером в UTC. Это не номер слайда
и не обещание точного времени исходного захвата на компьютере преподавателя.

## Временный файл и доставка

1. Сервер помещает копию JPEG в ограниченное хранилище RAM: не более 2 МиБ на файл,
   32 МиБ суммарно и 1024 файлов; срок жизни — десять минут. Диск и постоянная история
   снимков не используются. После перезапуска недоставленные временные файлы недоступны.
2. В outbox создаётся `DOCUMENT` для MAX identity этого участника. В `ref` находится
   только `/internal/v1/channels/max/media/{opaqueToken}` — случайный 256-битный ключ.
3. Адаптер забирает байты по этому внутреннему пути с `X-Internal-Api-Key`.
   Ни JWT студента, ни знание ссылки не заменяют внутренний ключ. Ответ — JPEG
   с `Cache-Control: no-store` и `Content-Disposition: attachment`.
4. При каждом скачивании проверяются действующий аккаунт и исходная MAX-привязка.
   После отзыва или истечения TTL файл возвращает `410` и удаляется из RAM.
5. Адаптер вызывает MAX `POST /uploads?type=file`, загружает multipart-поле `data`
   по выданному MAX URL и отправляет `attachments: [{type: "file", payload: {token}}]`.
   Ни внутренний ключ, ни токен бота не передаются серверу загрузки файла.

Адаптер принимает только указанный внутренний путь с корректным opaque-ключом,
не следует редиректам и ограничивает размер скачивания. Обработка произвольных
внешних ссылок для документов отсутствует. Токен загруженного MAX-файла повторно
используется при повторе outbox после `attachment.not.ready`; доступ к временному
исходному файлу при этом всё равно проверяется заново.

Уже запрошенный кадр может закончить доставку после остановки демонстрации:
это отдельный снимок, который участник явно запросил при действующем доступе.
Новые запросы после остановки или паузы запрещены. Отзыв аккаунта или привязки MAX
блокирует также последующее получение исходного файла адаптером.

## Проверка и источники

Unit и интеграционные тесты проверяют доступ, отсутствие неявного повторного входа,
получателя outbox, идемпотентность, TTL, ограничения памяти, сохранность байтов,
проверку внутреннего ключа и полный маршрут через локальные заглушки core/MAX.
Фактический приём и отображение JPEG-файла клиентами MAX требуют отдельной проверки
на устройствах; тесты не отправляют сообщения живым пользователям.

Протокол MAX проверен по официальным страницам 19.10.2026:

- [Загрузка медиафайлов](https://dev.max.ru/docs-api/methods/POST/uploads).
- [Отправка файлов и получение токена](https://dev.max.ru/docs-api/use-cases/sending-messages/media).
- [Отправка сообщений с вложениями](https://dev.max.ru/docs-api/methods/POST/messages).
