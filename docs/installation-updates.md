# Управляемые обновления установки

Выпуском обновлений управляет инфраструктура учреждения. Для интеграции доступны
административный API и внешний оператор Docker Compose/Kubernetes. MAX, браузер и API не получают
Docker socket, SSH-ключи или kubeconfig. GitLab не обязателен.

Это первая реализация управляемого **обновления приложения на существующей
топологии**. Обновление ОС, PostgreSQL, RabbitMQ, операторов Kubernetes и изменение
состава инфраструктуры выполняются отдельно системным администратором.
Смена всей инфраструктуры не маскируется под обновление веб-приложения.

## Как приходит новая версия

1. Команда проверяет конкретный commit, собирает образы и получает их digest.
2. Публикует описание релиза и подписанный Ed25519 каталог на постоянном HTTPS URL.
   Подписание: `deploy/updates/publish-catalog.py`; приватный ключ находится у
   выпускающей стороны/в защищённом CI, а не в установках учреждений.
3. Оператор каждой установки проверяет каталог и синхронизирует его с API примерно
   раз в минуту. API независимо проверяет подпись, срок, digest и диапазон схемы БД.
4. Для установки через оператор уполномоченный клиент создаёт задание через административный API.
   Если есть занятия, запрос ожидает их завершения. После окна обслуживания
   установка выполняется автоматически.

Merge в main, публикация подписанного каталога и установка в конкретном учреждении
— отдельные действия. GitLab/GitHub могут собрать, подписать и разместить каталог;
их deployment runner не требуется в каждой школе. Автоматическая публикация в
реальный реестр/хранилище потребует настройки секретов выпуска и адреса каталога;
само наличие кода не публикует релизы и не обновляет учреждения.

## Первая настройка учреждения

Нужна ручная первоначальная установка версии с поддержкой оператора: старый сервер
не сможет сам выполнить код механизма, которого в нём ещё нет.

- У API включить `INSTALLATION_UPDATES_ENABLED=true`, задать отдельный случайный
  `INSTALLATION_OPERATOR_KEY` длиной не менее 32 символов и доверенный публичный
  `INSTALLATION_RELEASE_PUBLIC_KEY` (Base64 DER Ed25519 или однострочный PEM).
- Скопировать `deploy/updates/operator.compose.example.json` или
  `operator.kubernetes.example.json` в закрытый конфигурационный файл с mode 600.
  Вписать каталог, публичный ключ, тот же операторский ключ и адрес API.
- Оператор запускается **на машине системного администратора**, где доступны
  существующая установка, Docker либо Kubernetes/SSH и резервные копии. Он сам
  делает исходящие запросы; привилегированный HTTP-порт не открывает.
- Запуск: `python3 deploy/updates/installation_operator.py --config /etc/lecturer-updates/operator.json`.
  Нужны Python 3.11+ и OpenSSL с Ed25519. Пример Linux-службы:
  `deploy/updates/lecturer-updates.service.example`. Служба не устанавливается
  автоматически и не меняет права учётной записи.

Оператор имеет права управления соответствующей установкой. Это доверенный
административный процесс; его конфигурация, журнал и ключ защищаются отдельно.
В частности, доступ к Docker остаётся у оператора, а не выдаётся приложению.

Compose-драйвер использует существующие cloud compose-файлы и тот же project,
что и резервное копирование. Для режима tunnel в `composeFiles` добавляется
`docker-compose.tunnel.yml`. Отдельный scalable Compose lab имеет иной backup
профиль и не считается автоматически поддержанным cloud-драйвером.
Kubernetes-драйвер использует `lecturer-k8s.sh kubectl` и его приватное состояние
кластера; backup и apply попадают в один кластер/namespace. Состав bindings нужно
сверить с установленными workloads. Пример включает content-worker в образ core,
event-publisher в services и edge в web.

Оператор использует `/api/v1/installation-operator/*` через обычный HTTPS адрес.
Эти маршруты проверяют отдельный `X-Installation-Key` и не принимают пользовательские
права вместо него. Внутренний alias сохранён для совместимости; открывать весь
`/internal` на публичном прокси не требуется.

## Что происходит при установке

- Подпись каталога и точные digest повторно проверяет сам оператор. Задание не
  содержит shell-команд, произвольного Git ref или URL установщика.
- Очередь и аудит хранятся в PostgreSQL. Повтор ключа запроса возвращает то же
  задание; уникальное ограничение допускает одно активное/неопределённое обновление.
- Оператор получает owner/fence/lease. Повторы этапов идемпотентны. Перед каждым
  изменением workloads повторно проверяется аренда.
- Барьер обслуживания берётся под тем же advisory lock, что и запуск/подключение
  новых занятий. Сначала проверяется отсутствие SCHEDULED/LIVE/PAUSED, затем
  запрет запуска фиксируется в той же транзакции. Проверки одного счётчика нет.
- Перед применением выполняется существующий проверяемый backup БД и blob-файлов.
  Compose создаёт пару; Kubernetes включает обе БД и настоящий blob PVC.
- Compose загружает digest, пересоздаёт выбранные сервисы с `--no-build --no-deps`
  и прежними volumes/secrets. Kubernetes меняет только образы существующих
  Deployment/DaemonSet, ждёт rollout и не записывает replicas поверх HPA.
- Миграции запускает приложение через Flyway. В этот канал допускаются только
  явно отмеченные обратно совместимыми релизы и подходящий диапазон исходной БД.
  Одной декларации недостаточно: совместимость проверяется при выпуске.
- Оператор сравнивает реальные image references с утверждёнными digest, проверяет
  готовность и публичный health. Только после этого записывается успех и снимается
  барьер. Локальные descriptors установщиков сохраняют новые digest.

## Сбой и восстановление

Потеря ответа не запускает второй job или второй этап. Повторные сетевые запросы
имеют ограниченный бюджет, нарастающую задержку и случайный разброс. Перезапуск
оператора с незавершённым локальным журналом требует проверки вместо слепого replay.

Ошибка backup не меняет приложение. Неопределённый результат после начала apply
переходит в «Требуется проверка». Новые занятия остаются закрыты до ручного
подтверждения администратора; истечение аренды после apply не открывает их само.
До apply аренда ограничена 15 минутами, чтобы оставшийся процесс подготовки не
блокировал учреждение навсегда.

Автоматического восстановления старой БД нет: оно может уничтожить записи после
backup. Оператор сохраняет предыдущие descriptors; возврат приложения или restore
копии выполняет системный администратор после проверки схемы и данных. После этого
он подтверждает ручную проверку через административный API. Это снимает блокировку очереди и не
выполняет никаких команд восстановления.

## Проверки и границы

- Java: реальная PostgreSQL, роли, подписи, очередь, idempotency/fencing,
  ожидание занятий, повтор после потери ответа, истёкшая аренда и admission barrier.
- Python: настоящие Ed25519 подписи OpenSSL, порядок backup/apply/verify, отказ
  backup, запрет replay и фиксированные Compose/Kubernetes команды.
- `deploy/updates/compose_drill.py` — отдельный настоящий Compose-проект с временным
  реестром, populated DB, synthetic additive migration и восстановлением backup.
  Скрипт удаляет только собственную лабораторию; основной стенд не использует.
- Браузер: админский сценарий, очередь/ожидание, неопределённый результат, узкий экран.

Результаты конкретных прогонов фиксируются отдельно. Проверка драйвера на mock
командах не заменяет обновление реального Kubernetes-кластера. Промышленная HA,
массовое видео и 10 000 пользователей обновлениями не подтверждаются.

Первичные протоколы: [OpenSSL Ed25519](https://docs.openssl.org/3.1/man1/openssl-pkeyutl/),
[Kubernetes rolling update](https://kubernetes.io/docs/tasks/run-application/update-deployment-rolling/),
[Docker Compose production](https://docs.docker.com/compose/how-tos/production/),
[GitLab deployments](https://docs.gitlab.com/ci/environments/deployments/).
