# Обновления установок учреждения

Цель: администратор видит версию, изменения и результат проверки, выбирает время
и запускает обновление из интерфейса Lecturer Assistant. Поддерживаются оба типа
установки: Docker Compose и Kubernetes. Наличие GitLab у учреждения не обязательно.

## Как устроить управление

Разработчики публикуют проверенный релиз: версия, точный SHA, образы по digest,
совместимость схемы, release notes и подписанный manifest. Merge в main запускает
тесты и сборку. Выпуск новой версии и обновление конкретного вуза — разные действия.

В интерфейсе администратор получает «Доступна версия», список изменений, требования
и кнопку «Обновить». Сервер проверяет роль ADMIN, доверенную подпись и совместимость;
принимает только ID релиза из каталога, а не произвольный URL/команду/ветку.
Запрос имеет idempotency key; конкурентный повтор не начинает вторую установку.

Установку выполняет отдельный локальный оператор. Web/API не получает Docker socket,
root SSH или kubeconfig. Оператор имеет ровно один драйвер площадки:

- Compose: загрузить образы по digest, сохранить прежний release descriptor,
  выполнить миграцию и пересоздать нужные сервисы с прежними volumes/secrets.
- Kubernetes: применить проверенный manifest, выполнить migration job и дождаться
  readiness/rollout. HPA сохраняет владение replicas, SFU обновляется после drain.

Протокол задания одинаковый для обоих драйверов: очередь, lease/fencing, этап,
прогресс, ошибка, конечный статус и аудит. Если API перезапускается при обновлении,
состояние задания сохраняется и оператор продолжает от зафиксированного этапа.

## Последовательность

1. Проверить место, доступность образов, конфигурацию, совместимость и права.
2. Дождаться окна без текущих занятий; запретить запуск новых на время обновления
   с ограниченным по времени maintenance lease. Один предварительный SQL-запрос
   без такого барьера не защищает от занятия, начавшегося сразу после проверки.
3. Создать и проверить согласованную резервную копию БД и файлов; зафиксировать
   прежние версии образов и схемы. Analytics хранится отдельно и может перестраиваться.
4. Применить совместимую миграцию и обновить сервисы, проверить API, realtime,
   worker и интерфейс. Записать результат, снять maintenance lease.
5. При ошибке остановить продолжение и показать причину. Автоматический возврат
   приложения допустим только при совместимой схеме. Восстановление старой БД
   после появления новых записей требует отдельного решения: иначе потеряются данные.

Нельзя обещать обновление без риска только потому, что используются Docker volumes
и CI. До включения кнопки нужны тесты миграции populated DB, восстановления копии,
срыва каждого этапа, потери оператора и параллельного запуска занятия.

## GitLab учреждения

Если вуз использует GitLab, оператор может запускать утверждённый deployment job
в его окружении вместо собственного apply. В GitLab доступны ручные deployments
и история окружений; расширенные approval-возможности зависят от редакции.
Встроенный GitLab/runner — один из backend-ов, а не обязательное условие продукта.

Официальная основа:
[GitLab deployments](https://docs.gitlab.com/ci/environments/deployments/),
[deployment approvals](https://docs.gitlab.com/ci/environments/deployment_approvals/),
[Docker Compose production](https://docs.docker.com/compose/how-tos/production/).
