# Параллельные лекции: текущее состояние и проверка ёмкости

## Что уже изолировано

- Преподаватели, курсы, лекции и запуски имеют отдельные ID. Доступ к управлению проверяется по курсу.
- Студенты и события привязаны к `session_id`; SSE-клиенты группируются по коду конкретной лекции.
- Несколько лекций могут быть активны одновременно. Поиск пульта преподавателя фильтруется по `created_by`.
- Передача слайдов студентам идёт через SSE; браузер скачивает PNG при смене ссылки. Отправки ботом MAX каждому студенту на каждое переключение нет: веб-участие имеет канал `web`, а fanout бота выбирает только совпадающий канал идентичности.

Интеграционный тест `ParallelLectureIntegrationTest` проверяет двух преподавателей с разными курсами: у каждого своя активная лекция, чужой курс недоступен, студенты и сигналы не смешиваются. Это проверка корректности, не измерение предельной нагрузки.

## Что действительно измерено

25.09.2026 на отдельном Compose-стеке ревизии `12856ce` проверена **одна** лекция со 150 SSE-клиентами: 150/150 подключений, 22 500 событий, p95 доставки смены слайда 1 648 мс, 0 ошибок HTTP и SSE. Первичные данные: `e2e/reports/20260925T102700Z-12856ce/`. Замер не подтверждает ни 2×150, ни 10×150, ни текущую ревизию.

## Узкие места и принятые меры

| Узел | Риск при 10×150 | Текущее действие |
|---|---|---|
| SSE-тик | Последовательный обход 10 лекций задерживает поздние секции | Блоки лекций обрабатываются ограниченным пулом из 4 работников; для одной лекции не накапливается больше одной ожидающей отправки |
| PostgreSQL | Запросы личного состояния и поиска активной лекции | Один общий снимок на лекцию за тик, персонализация пачкой; индексы по активному участнику и создателю сессии |
| Подключение через один университетский NAT | Старый IP-лимит 120 входов/мин и 120 сигналов/мин отклонял бы массовый вход | Пределы установки подняты до 3000 входов MAX/мин и 6000 сигналов/мин; оба значения настраиваются переменными окружения |
| Изображения | Одновременное переключение 10 секций создаёт всплеск PNG-загрузок | Стабильные подписанные URL и кэш клиента; нужны замеры трафика и p95 на 1500 клиентах |
| Масштабирование ядра | SSE-клиенты и простой STOMP-брокер находятся в памяти одного процесса | Для пилота используется один core. Для нескольких реплик нужен внешний pub/sub или брокер и стратегия маршрутизации; обычное увеличение числа реплик без этого приведёт к потере событий |

Пул из 4 работников снижает взаимное ожидание секций, но не заменяет измерение ёмкости. Вход через MAX проходит криптографическую проверку `initData`; IP-лимит остаётся защитным верхним порогом, а не квотой на отдельного студента.

## Условие допуска для 10 параллельных секций

1. Создать в **изолированном** Compose-стеке 10 разных активных лекций и 10 преподавателей; подготовить разные коды. Публичный стенд не нагружать синтетическими участниками.
2. Прогнать `e2e/k6/student-sse.js` сначала с `JOIN_CODES` из 2 кодов и `VUS=300`, затем с 10 кодами и `VUS=1500`. Каждый клиент должен открыть SSE и скачать текущий PNG; отдельно запланировать одновременные смены слайдов в разных секциях.
3. Зафиксировать на текущем commit: долю успешных входов/SSE/PNG ≥99%, p95 доставки каждого переключения <2 с, отсутствие 429/5xx, память core и число соединений PostgreSQL без роста в течение 30 минут. Измерить p95 отдельно по каждой лекции, чтобы среднее не скрыло голодающую секцию.
4. Если порог не пройден, сначала измерить, где задержка (SSE-тик, БД, PNG, прокси), затем настроить число работников, пул БД, кэш и ресурсы контейнеров по результату. При необходимости нескольких реплик перейти на внешний pub/sub до масштабирования.

**Статус:** параллельность по данным и правам проверяется тестом. Заявлять доказанную ёмкость «10 преподавателей × 150 студентов» пока нельзя; нужен описанный нагрузочный прогон на целевой машине.
