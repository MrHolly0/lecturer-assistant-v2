# Параллельные лекции: текущее состояние и проверка ёмкости

## Что уже изолировано

- Преподаватели, курсы, лекции и запуски имеют отдельные ID. Доступ к управлению проверяется по курсу.
- Студенты и события привязаны к `session_id`; SSE-клиенты группируются по коду конкретной лекции.
- Несколько лекций могут быть активны одновременно. Поиск пульта преподавателя фильтруется по `created_by`.
- Передача слайдов студентам идёт через SSE; браузер скачивает PNG при смене ссылки. Отправки ботом MAX каждому студенту на каждое переключение нет: веб-участие имеет канал `web`, а fanout бота выбирает только совпадающий канал идентичности.

Интеграционный тест `ParallelLectureIntegrationTest` проверяет двух преподавателей с разными курсами: у каждого своя активная лекция, чужой курс недоступен, студенты и сигналы не смешиваются. Это проверка корректности, не измерение предельной нагрузки.

## Что действительно измерено

25.09.2026 на отдельном Compose-стеке ревизии `12856ce` проверена **одна** лекция со 150 SSE-клиентами: 150/150 подключений, 22 500 событий, p95 доставки смены слайда 1 648 мс, 0 ошибок HTTP и SSE. Первичные данные: `e2e/reports/20260925T102700Z-12856ce/`. Замер не подтверждает ни 2×150, ни 10×150, ни текущую ревизию.

27.09.2026 на отдельном Compose-стеке основы `c2c504c` с текущими исправлениями
проверены 10 независимых преподавателей и лекций по 150 студентов. Генератор k6
подключался по внутренней сети Compose; вход 1500 студентов распределён на 75 секунд,
после чего все преподаватели одновременно переключили четыре слайда. При штатных
четырёх SSE-работниках: **1500/1500 входов, полных SSE-сценариев и клиентов с
изображениями**, 7500/7500 загрузок PNG, все 7500 снимков относятся к своей лекции,
худший p95 доставки слайда в отдельной секции — **390 мс**. Один core занимал около
1 ГиБ памяти, PostgreSQL — около 90 МиБ; 11 подключений к БД. Исходные метрики и
все неудачные сравнения: `e2e/reports/20260927-parallel-lectures/`.

Прогоны через опубликованный порт Docker Desktop были нестабильны: в диагностике
обнаружены `dial: i/o timeout` со статусом 0 до ответа приложения. Поэтому результат
внутренней сети подтверждает ёмкость ядра в этой конфигурации, но не доказывает
стабильность внешнего прокси или публичного стенда. Четыре работника на внутренней
сети показали результат не хуже десяти; значение по умолчанию оставлено 4.

В отдельном 30-минутном прогоне на внутренней сети 1500 клиентов открыли SSE,
память core оставалась около 1,1 ГиБ, а 1497 соединений сохранялись до 25-й минуты.
Одноразовые потоки закрылись по штатному 30-минутному тайм-ауту; массовое
переподключение браузеров этим прогоном не проверено. При прогоне через локальный
Caddy все 1500 клиентов вошли, но за лимит 180 секунд завершили полный сценарий
лишь 299. Это не подтверждает ёмкость 10×150 через прокси; причины незавершения
сценариев требуют отдельного разбора. Публичный туннель не нагружался.

## Узкие места и принятые меры

| Узел | Риск при 10×150 | Текущее действие |
|---|---|---|
| SSE-тик | Последовательный обход 10 лекций задерживает поздние секции | Блоки лекций обрабатываются ограниченным пулом из 4 работников; для одной лекции не накапливается больше одной ожидающей отправки. Параметр `SSE_BROADCAST_WORKERS` доступен в Compose |
| 30-минутный срок SSE | Подключившиеся одновременно студенты могут почти одновременно переподключаться | Веб-клиент открывает поток снова и при повторных ошибках опрашивает снимок; массовое переподключение нужно проверять отдельно от одного непрерывного SSE-потока |
| PostgreSQL | Запросы личного состояния и поиска активной лекции | Один общий снимок на лекцию за тик, персонализация пачкой; индексы по активному участнику и создателю сессии |
| Подключение через один университетский NAT | Старый IP-лимит 120 входов/мин и 120 сигналов/мин отклонял бы массовый вход | Пределы установки подняты до 3000 входов MAX/мин и 6000 сигналов/мин; оба значения настраиваются переменными окружения |
| Изображения | Одновременное переключение 10 секций создаёт всплеск PNG-загрузок | Стабильные подписанные URL и кэш клиента; 7500 тестовых PNG скачались без ошибок, тяжёлые реальные презентации ещё не проверены |
| Масштабирование ядра | SSE-клиенты и простой STOMP-брокер находятся в памяти одного процесса | Для пилота используется один core. Для нескольких реплик нужен внешний pub/sub или брокер и стратегия маршрутизации; обычное увеличение числа реплик без этого приведёт к потере событий |

Пул из 4 работников снизил взаимное ожидание секций в проведённом тесте; результат
относится к указанной машине и тестовым слайдам. Вход через MAX проходит
криптографическую проверку `initData`; IP-лимит остаётся защитным верхним порогом,
а не квотой на отдельного студента.

## Условие допуска для 10 параллельных секций

1. Создать в **изолированном** Compose-стеке 10 разных активных лекций и 10 преподавателей; подготовить разные коды. Публичный стенд не нагружать синтетическими участниками.
2. Прогнать `e2e/k6/student-sse.js` сначала с `JOIN_CODES` из 2 кодов и `VUS=300`, затем с 10 кодами и `VUS=1500`. Каждый клиент должен открыть SSE и скачать текущий PNG; отдельно запланировать одновременные смены слайдов в разных секциях.
3. Зафиксировать на текущем commit: долю успешных входов/SSE/PNG ≥99%, p95 доставки каждого переключения <2 с, отсутствие 429/5xx, память core и число соединений PostgreSQL без роста в течение 30 минут. Измерить p95 отдельно по каждой лекции, чтобы среднее не скрыло голодающую секцию.
4. Если порог не пройден, сначала измерить, где задержка (SSE-тик, БД, PNG, прокси), затем настроить число работников, пул БД, кэш и ресурсы контейнеров по результату. При необходимости нескольких реплик перейти на внешний pub/sub до масштабирования.

**Статус:** параллельность по данным и правам проверена интеграционным тестом;
изолированное ядро прошло 10×150 по внутренней сети и 30-минутное удержание
соединений без роста памяти. Прогон через локальный Caddy не завершил полный
сценарий для 1201 из 1500 клиентов. До заявления гарантированной ёмкости публичной
установки нужны проверка прокси и переподключения, затем замер на тяжёлых реальных
презентациях.
