Ты отвечаешь за серверную часть проекта `lecturer-assistant-v2` на хакатоне MAX. Дедлайн отправки — 30.09.2026, до заморозки функций 27.09 вечером.

## Контекст

Модульный монолит Spring Boot (Java 21), PostgreSQL, Flyway, сборка Maven. Каталог `core/`, модули: `iam`, `org`, `content`, `live`, `feedback`, `qa`, `interaction`, `channel`, `analytics`. Адаптеры мессенджеров — отдельные Node-процессы в `adapters/`, образец `adapters/telegram/telegram-adapter.mjs`.

Продукт: преподаватель ведёт лекцию, студенты в мини-приложении MAX видят текущий слайд, шлют сигналы понимания, задают вопросы и отвечают на вопросы-проверки.

Обязательно прочитать до начала:

- `docs/hackathon/research/MAX_API_NOTES.md` — справка по API MAX: вебхук, лимит 30 rps, `?startapp=`, алгоритм проверки `initData`.
- `docs/hackathon/research/DEFECTS.md` — 27 дефектов с файлами и строками.
- `docs/hackathon/research/PACKAGING_GAPS.md` — требования к упаковке и замер сборки.
- `docs/hackathon/TEAM_TASKS.md` — формулировки задач B-01…B-17.

## Границы

Твои каталоги: `core/src`, `adapters/` (кроме Dockerfile), `openapi/`, миграции. Каталог `web/` не трогаешь — там работает фронтенд. Dockerfile, compose, `deploy/`, `.env.example`, README и стенд — зона потока упаковки (`BRIEF_PACKAGING.md`). Нужны изменения там — пишешь оркестратору.

Контракт API меняешь только через оркестратора: фронтенд пишет код против него с первого дня.

## Правила

- База — `v2/phase-5-web-student-channel`, ветки `main` в репозитории нет. Ветка на задачу: `feat/B-04-participant-identity`, от актуальной базы. Коммит начинается с номера задачи.
- Секреты только в `.env` на сервере и в менеджере паролей. В репозиторий не попадает ни токен бота, ни `JWT_SECRET`, ни ключ адаптера.
- Каждая правка дефекта сопровождается тестом, который падал до неё.
- Схема базы меняется только миграцией Flyway, правка старых миграций запрещена.
- Перед тем как сказать «готово», проверяешь критерий приёмки на стенде, а не локально.
- Если задача занимает больше половины дня или упирается в неизвестное — пишешь оркестратору сразу, не в конце дня.

## Очередь работ

**День 1 (18.09), приоритет сверху вниз**

1. **B-02, вход по MAX.** `POST /api/v1/auth/max` принимает `initData`, проверяет подпись по алгоритму из справки (`secret_key = HMAC_SHA256("WebAppData", токен_бота)`), проверяет свежесть `auth_date`, находит или создаёт человека по MAX `user.id`, возвращает JWT и роль. Тесты: подделанная подпись, просроченный `auth_date`, повторный вход одного пользователя не создаёт второго человека.
2. **B-04, личность участника.** Убрать создание эфемерного человека на каждый вход (`StudentWebSessionService.java:91–110`, дефект D-01). Участник лекции — это человек; повторный вход возвращает того же участника. В участники курса студент добавляется один раз. Анонимный вход по коду остаётся запасным путём.
3. **B-05, опросы.** Дефекты D-02 и D-08: закрытый опрос остаётся в снапшоте с правильным ответом и распределением; до закрытия распределение студенту не отдаётся; ответ проверяет принадлежность `pollId` сессии; повторный ответ не засчитывается.

**День 2–3 (19.09, 22.09)**

4. **B-01, адаптер MAX.** Новый `adapters/max` по образцу telegram-адаптера: вебхук, `bot_started` с payload, `/start`, кнопка `open_app`, отправка сообщений из outbox с учётом лимита 30 rps. Токен — из переменной окружения.
5. **B-10, стенд** — передан в поток упаковки (P-04). Твоя часть: вебхук адаптера должен работать за Caddy на HTTPS, как только стенд поднят.
6. **B-03, роль преподавателя.** Привязка MAX-аккаунта к преподавателю по приглашению, одноразовая ссылка на проектор (живёт 2 минуты, открывает только свою лекцию).

**День 4–6 (23–26.09)**

7. **B-06, сигналы по слайдам.** Миграция: номер слайда в сигнале. Смена слайда сбрасывает актуальное состояние. Агрегат по текущему слайду и список проблемных слайдов (дефект D-04).
8. **B-07, вопросы студентов.** Ответ преподавателя, закрытие, список вопросов студента, событие в поток (дефект D-05).
9. **B-09 + D-03, слайды.** Подпись ссылки на слайд должна зависеть от окна времени, а не от текущей секунды, иначе каждый студент перекачивает картинку раз в секунду. Это узкое место на 150 студентах.
10. **D-10, изоляция данных.** В `PollController`, `ActivityController`, `QuestionBankController` проверять принадлежность `pollId`, `runId`, `questionId`, `sessionId` курсу. Образец правильной проверки — в модулях `live` и `content`.
11. **B-08, итоги лекции.** Сводка преподавателю и конспект студенту, рассылка сообщений через outbox при завершении.

**День 7–9 (27–29.09)**

12. **B-12, API.** Актуальный OpenAPI: не хватает `GET /api/v1/config/channels`, пути `/internal/v1/...` разворачиваются неверно, адреса стенда и примеров запросов нет. `DATA-API.yaml` и тестовые данные делает поток упаковки, ты отвечаешь за соответствие OpenAPI коду.
13. **B-13, безопасность.** CORS, ограничение частоты входа и сигналов, убрать `setAllowedOriginPatterns("*")`, в логи не попадают токены и `initData`, защита от повторного использования `initData`, одноразовый билет для потока событий вместо токена в строке запроса (D-12).
14. **B-17, метрики.** События для метрик пилота и SQL выгрузки (`docs/hackathon/research/PILOT_METRICS.md`), поле `origin` уже есть.

Docker, compose, время сборки, README и тестовые данные — поток упаковки, `BRIEF_PACKAGING.md`.

## Контракт с фронтендом

Фиксируется до начала работы, меняется только через оркестратора.

| Метод и путь | Запрос | Ответ |
|---|---|---|
| `POST /api/v1/auth/max` | `{ initData }` | `{ accessToken, expiresIn, role, personId, displayName }` + `Set-Cookie` с refresh-токеном (`HttpOnly`, `Secure`; `SameSite` уточняется после проверки веб-версии MAX на фрейм) |
| `GET /api/v1/me/active-session` | — | `{ sessionId, courseId, joinCode, lectureTitle, currentSlideIdx }` или 204 |
| `GET /api/v1/student/sessions/{joinCode}` | — | снапшот: `status`, `lectureTitle`, `currentSlide`, `slideCount`, `signalAggregate`, `activePoll` (в том числе закрытый, с `correctOptionIdx` и `votes`), `myVote`, `myQuestions` |
| `POST /api/v1/student/sessions/{joinCode}/signals` | `{ value, slideIdx }` | агрегат по текущему слайду |
| `POST /api/v1/student/sessions/{joinCode}/polls/{pollId}/respond` | `{ optionIdx }` | `{ accepted, myVote }`, распределение только после закрытия |
| `GET /api/v1/courses/{courseId}/sessions/{sessionId}/engagement` | — | сигналы по текущему слайду, проблемные слайды, вопросы со статусами |
| `POST /api/v1/courses/{courseId}/sessions/{sessionId}/questions/{questionId}/answer` | `{ text }` | вопрос со статусом и ответом |
| `GET /api/v1/courses/{courseId}/sessions/{sessionId}/summary` | — | итог лекции |
| `GET /api/v1/student/sessions/{joinCode}/summary` | — | конспект студента |

Авторизация участника после входа через MAX — обычный JWT, отдельный `participantToken` для таких пользователей не нужен. Токен участника для анонимного входа сохраняется и не передаётся в строке запроса (дефект D-12).

Реализовано 18.09 (B-02, коммит `81b26c2`): срок жизни `initData` — 1 час (`MAX_INIT_DATA_MAX_AGE`), человек ищется по MAX `user.id` в `iam.channel_identities`. На реальном `initData` из MAX ещё не проверено: нет токена бота.

Дополнение 18.09 (B-04, коммит `fd9b4a6`): `POST /api/v1/student/sessions/{joinCode}/join` возвращает `participantToken` всегда, в том числе при входе с JWT. Токен нужен только для потока событий (`EventSource` не передаёт заголовки), остальные запросы идут с `Authorization: Bearer`. Замена на одноразовый билет — в D-12 вместе с B-13. Анонимный вход принимает `participantToken` в теле и возвращает того же участника; в участники курса гость не попадает.

Дополнение 18.09 (B-05, коммит `319af2d`):
- Снапшот и `GET .../polls/active` отдают открытый опрос, а если его нет — последний закрытый; закрытый остаётся до старта следующего.
- Пока опрос открыт, `activePoll.votes` и `activePoll.correctOptionIdx` равны `null`. Код, который строит полосы распределения, обязан это проверять.
- `myVote` приходит только в `GET /api/v1/student/sessions/{joinCode}` при идентификации через `Authorization: Bearer` или заголовок `X-Participant-Token`. В событиях потока `myVote` всегда `null`: клиент не должен затирать им уже известное значение.
- `POST .../polls/{pollId}/respond` отвечает `200 { accepted, myVote }` вместо 204. Первый ответ фиксируется, повторный и ответ после закрытия дают `accepted: false`.
- Ответ на опрос или активность чужой сессии даёт 404.
- `GET .../polls/active` без единого опроса в сессии по-прежнему даёт 404 (нормализация — D-18).
- Анонимный вход с пустым именем получает имя «Гость …» вместо ошибки 400.

Как только контракт по эндпоинту меняется, ты в тот же час обновляешь `openapi/lecturer-assistant-v2.yaml` и пишешь оркестратору.

Дополнение 24.09 (B-03, привязка MAX к преподавателю). Контракт зафиксирован, реализуется параллельно бэкендом и фронтендом:

| Метод и путь | Запрос | Ответ |
|---|---|---|
| `POST /api/v1/identity/max/link-codes` (нужен JWT преподавателя из браузера) | — | `{ code, expiresAt }`, код из 6 символов A–Z и 0–9, живёт 5 минут, одноразовый |
| `POST /api/v1/auth/max` | `{ initData, linkCode? }` | как раньше; если передан валидный `linkCode`, MAX-аккаунт связывается с этим человеком и в ответе приходит его роль. Невалидный или просроченный код — 400, уже использованный — 409 |
| `GET /api/v1/me/active-session` | — | `{ sessionId, courseId, joinCode, lectureTitle, currentSlideIdx }` или 204, если идущей лекции нет |

Без кода вход через MAX по-прежнему создаёт студента. Повторный вход того же MAX-пользователя берёт роль из уже связанной личности, код больше не нужен.
