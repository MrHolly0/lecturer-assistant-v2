## 3. Продукт и сценарий

**Продукт.** Бот MAX с мини-приложением. Помогает преподавателю увидеть во время занятия, что группа перестала понимать материал, и сразу проверить объяснение коротким вопросом.

**Пользователи.** Преподаватели потоковых лекций младших курсов технического вуза и их студенты. Сегмент подтверждается интервью (см. раздел 8).

**Основной сценарий:**

1. Преподаватель открывает мини-приложение MAX на компьютере и запускает подготовленную лекцию.
2. На проектор выводятся QR и ссылка `max.ru/<бот>?startapp=<код>`.
3. Студент открывает ссылку в MAX и попадает в лекцию без регистрации: личность берётся из MAX.
4. Слайды приходят студенту вслед за преподавателем. Студент нажимает «Понятно / Есть вопрос / Не понимаю», сигнал привязан к слайду.
5. Преподаватель видит, на каком слайде растёт «Не понимаю», и получает вопросы.
6. Преподаватель объясняет иначе и запускает вопрос-проверку. Студенты отвечают, чужие ответы до закрытия не видны.
7. После закрытия студент видит правильный ответ и свой результат, преподаватель — распределение.
8. После лекции бот присылает преподавателю итог, студенту — конспект с его непонятными слайдами и ответами.

**Устройства.** Всё внутри MAX как мини-приложение. У преподавателя основное устройство — компьютер, планшет и телефон получают адаптивную раскладку. Студент работает с телефона или в веб-MAX. Проектор открывается отдельным окном браузера по одноразовой ссылке.

Три слова, которые дальше встречаются постоянно: рабочее место — весь кабинет преподавателя; презентер — экран показа слайдов; пульт — телефон преподавателя в идущей лекции.

**Не делаем:** Telegram и ВК в интерфейсе, нативные приложения, генерацию материалов, интеграции с LMS, полный банк активностей.

## 4. Решения по архитектуре

| Решение | Почему |
|---|---|
| Основа — v2: модульный монолит Spring Boot (Java 21) + React/Vite + PostgreSQL | Роли, курсы, импорт презентаций и веб-путь студента уже есть; v1 завязана на Telegram |
| Бот + мини-приложение | Слайды и сигналы в чатовом диалоге неудобны; задание требует мини-приложение, подключённое к боту |
| Одна веб-сборка для всех ролей и устройств | Один код; MAX-режим включается при наличии `window.WebApp` |
| MAX-адаптер — отдельный процесс `adapters/max` по схеме Telegram-адаптера (ADR-004) | Ядро не зависит от мессенджера, есть официальная JS-библиотека |
| Вход — проверка подписи `initData` на сервере, затем обычный JWT | Без паролей; `initDataUnsafe` не доказательство |
| Интерфейс мини-приложения на MAX UI, если позволяет лицензия | Нативный вид, светлая и тёмная темы |
| Стенд: VPS + домен + Caddy (HTTPS) + docker compose | Для вебхука и мини-приложения нужен постоянный HTTPS-адрес на весь период оценки |

## 5. Состояние кода: что есть

Репозиторий `lecturer-assistant-v2`, ветка `v2/phase-5-web-student-channel`, около 7,6 тыс. строк Java и 16 тыс. строк фронтенда.

Модули ядра: `iam` (пользователи, роли, JWT, приглашения), `org` (курсы, группы, участники), `content` (импорт PDF/PPTX, слайды, заметки, лекции), `live` (сессии, участники, SSE), `feedback` (сигналы), `qa` (вопросы), `interaction` (быстрые опросы, банк вопросов, GIFT, активности), `channel` (адаптеры каналов, outbox), `analytics` (события).

Работает: регистрация и вход по ролям, курсы и приглашения, импорт презентации с прогрессом, лекции и живые сессии, показ слайдов с рисованием, проектор, экран подключения с QR, веб-путь студента (сигналы, вопросы, быстрые опросы), SSE-обновления, нагрузочный прогон на 150 студентов, PWA-оболочка.

Фронтенд: React 18, Vite, TanStack Query, Tailwind, Radix, компоненты в `web/src/shared/ui`.

Инфраструктура: `docker-compose.yml` и профили dev/prod/tunnel/standalone, Flyway-миграции V1–V11, OpenAPI в `openapi/lecturer-assistant-v2.yaml`, адаптеры `adapters/telegram` и `adapters/echo`.

Интеграции с MAX нет: ни адаптера, ни проверки `initData`, ни ссылок MAX. В конфигурации каналов Telegram и ВК.

## 6. Состояние кода: что сломано

Проверено чтением кода и прогоном на стенде 17.09; полный список из 27 дефектов — в разделе 12.

| Проблема | Где | Следствие |
|---|---|---|
| Каждый вход по коду создаёт временного человека и добавляет его в участники курса | `StudentWebSessionService.join` | Повторный вход = новый участник, курс засоряется, история студента невозможна |
| Закрытый опрос исчезает из снапшота студента | `PollService.activePollForSession` | Студент не видит правильный ответ. Подтверждено в браузере |
| Не проверяется принадлежность `pollId` и `runId` сессии | обработка ответов студента | Ответ в чужую лекцию |
| Сигнал понимания хранится без номера слайда и не сбрасывается | `FeedbackRepository` | Нет проблемных слайдов, сигнал «залипает» |
| У вопросов нет ответа и закрытия, список на фронте живёт в памяти страницы | `qa`, `StudentSessionPage` | После перезагрузки вопросы пропадают, преподаватель не может ответить |
| Истечение токена выбрасывает из лекции | фронтенд | Лекция длиннее срока жизни токена прерывается |
| Банк вопросов и активности не подключены к интерфейсу | `interaction`, презентер | Готовый бэкенд не используется |
| Аналитика пишет только вход, сигнал и вопрос | `analytics` | Метрики пилота посчитать не из чего |

Интерфейс студента на телефоне: мелкий слайд, кнопка отправки уходит за край и перекрывается уведомлением, статус «LIVE» по-английски, «1 ответов», выбранный сигнал почти не выделен, после ответа сразу видно распределение.

Интерфейс преподавателя: восемь кнопок в шапке, включая «Завершить»; опрос раскрывается в шапке; код подключения показан дважды; вкладки Telegram и ВК; путь до запуска лекции идёт через длинную страницу материалов.

## 10. Справка по API MAX

Полностью: [research/MAX_API_NOTES.md](research/MAX_API_NOTES.md), 570 строк со ссылками на страницы документации. Главное для планирования:

- **Bot API:** `https://platform-api2.max.ru`, заголовок `Authorization: <token>` без `Bearer`, лимит 30 запросов в секунду. Вебхук — `POST /subscriptions` с телом `{url, update_types, secret}`, только HTTPS и сертификат доверенного удостоверяющего центра; секрет возвращается в заголовке `x-max-bot-api-secret`. Long polling для продакшена запрещён документацией.
- **Две разные ссылки, их легко перепутать:** `?start=` открывает бота, payload до 128 символов, приходит в событии `bot_started`; `?startapp=` открывает мини-приложение, payload до 512 символов, алфавит `[A-Za-z0-9_-]`, приходит в `start_param`. Код лекции кодируем Base64url без padding.
- **Кнопка `open_app`** открывает мини-приложение из сообщения бота; в клавиатуре не больше трёх таких кнопок в ряду.
- **Мини-приложение подключается только скриптом с CDN**, npm-пакета для Bridge нет: типы описываем сами, версию зафиксировать нельзя.
- **Ограничения Bridge:** `SecureStorage`, `DeviceStorage` и `HapticFeedback` не работают в веб- и десктопной версии MAX. Значит сессию студента храним только на бэкенде, а вибрацию в пульте считаем необязательной. Кнопки `MainButton` в MAX нет.
- **Валидация `initData`:** секретный ключ — `HMAC_SHA256(key="WebAppData", message=токен бота)`, именно в таком порядке. В справке пошаговый алгоритм, псевдокод и таблица типичных ошибок.
- **Публикация:** нужен верифицированный профиль организации, ИП (до 5 ботов) или самозанятого (2 бота). Модерация до 48 часов в рабочие дни. Никнейм генерируется автоматически в формате `idИНН_bot` — красивой ссылки для QR не будет, это влияет на макеты экрана подключения и на презентацию.
- **SDK:** официальные библиотеки есть для TypeScript (`@maxhub/max-bot-api`, MIT), Go и Python. Для Java и Kotlin официального SDK нет — подтверждает решение делать адаптер отдельным Node-процессом.

Что осталось неясным и требует проверки на практике или вопроса организаторам: обязательный набор полей `open_app` и доходит ли его `payload` до мини-приложения; работает ли загрузка файлов из мини-приложения; размеры окна на компьютере; рекомендуемый срок жизни `auth_date`; политика повторов вебхука и защита от повторной отправки. Противоречия в самой документации: тип `start_param`, требуемая версия React для MAX UI и лицензия MAX UI.

## 11. Готовность к сдаче

Полностью: [research/PACKAGING_GAPS.md](research/PACKAGING_GAPS.md), 352 строки, проверка читающая. Факты перепроверены на текущем состоянии базы, где уже есть B-02, B-04 и B-05. Каркас есть: три Dockerfile, пять compose-файлов, `.dockerignore`, `.env.example` на 19 ключей, CI со сборкой образов. Секретов в рабочем дереве и во всей истории (34 коммита, 9 веток) не найдено.

Блокирующие расхождения:

1. `docker compose up` не поднимает адаптеры каналов: у них нет ни Dockerfile, ни сервиса в compose. Требование «все локальные компоненты одной командой» не выполняется.
2. README не закрывает ни один из двенадцати обязательных разделов: 32 строки, половина — «быстрый старт фазы 0», запуск требует `mvn verify` и `npm run build` до compose.
3. Нет тестовых учётных записей и тестовых данных: после запуска проверяющий попадает на пустую базу и упирается в приглашения.
4. Нет `DATA-API.yaml`.
5. Сборка не укладывается в норматив кратно. Замер на Apple M4 Pro с прогретыми базовыми образами: конвертер — **1887 секунд (31 минута 27 секунд)**, ядро и веб — **470 секунд (7 минут 50 секунд)**, полная сборка одной командой — около **31,5 минуты против норматива 5 минут**. Повторная сборка со слоевым кэшем — 1 секунда.

Виновники названы точно. В конвертере одна строка `deploy/converter/Dockerfile:3–8`: `apt-get install libreoffice` без фиксации версий тянет 206 пакетов и 153 МБ, образ вырастает до 991 МБ, и это 1871 секунда из 1887. Метапакет ставит Writer, Calc, Base и Java-стек, хотя конвертеру нужен только Impress. В ядре из 468 секунд стадии Maven 293 секунды уходят на загрузку до первого плагина: `core/Dockerfile:3–6` кладёт исходники в один слой с `pom.xml`, слоя прогрева нет, тестовые зависимости (около 40 МБ) качаются даже при пропуске тестов.

Исправление — около 8 часов. Без переделки конвертера норматив не выполнится ни на каком канале.

Общая оценка объёма по упаковке и документации: **около 40 часов**, с задачей по безопасности B-13 — около 44. При одном бэкенд-разработчике это пять рабочих дней, то есть почти весь остаток до заморозки кода.

|---|---|---|
| D-01 | Вход создаёт нового человека и участника курса | Повторный вход = новый участник, счётчик «на связи» и светофор врут |
| D-02 | Закрытый опрос исчезает у студента и у преподавателя | Снапшот ищет только открытый опрос; панель преподавателя схлопывается через 1,5 с |
| D-03 | Подпись ссылки на слайд пересчитывается от текущего времени | Ссылка меняется каждую секунду, каждый студент перекачивает картинку слайда раз в секунду, кэш сервис-воркера промахивается. Это и рвётся на 150 студентах; нагрузочный тест этого не ловит, потому что картинки не качает |
| D-04 | Сигнал — одна строка на человека на всю лекцию | Нет номера слайда, смена слайда ничего не сбрасывает, баннер «не понимают» залипает |
| D-05 | У вопроса нет ответа и закрытия | Колонки и статусы в базе есть, кода нет; список вопросов у студента живёт в памяти вкладки |
| D-06 | 401 стирает токен без попытки обновления | При сроке жизни 15 минут преподаватель вылетает на вход посреди лекции; WebSocket с просроченным токеном молча не переподключается |
| D-07 | Вход без имени молча не срабатывает | Сервер требует имя от двух символов, на фронте нет обработки ошибки: студент жмёт «Подключиться» и ничего не происходит |
| D-08 | Распределение ответов видно до закрытия опроса | Подсказка большинству; снапшот публичный, распределение читается даже без участия |

Отдельно стоит **D-10**: — в контроллерах опросов, активностей и банка вопросов проверяется только доступ к курсу, но не принадлежность `pollId`, `runId`, `questionId` и `sessionId` этому курсу. Любой преподаватель со своим курсом может прочитать чужой банк вопросов с правильными ответами, персональные ответы чужих студентов и запустить опрос в чужой идущей лекции. В модулях `live` и `content` это сделано правильно — есть с чего копировать.

Остальные важные: токен участника уходит в строке запроса SSE (D-12), рассылка SSE идёт одним потоком и на каждом тике тянет весь дек (D-13), эфемерные люди не чистятся (D-14), нет индексов под запросы движка взаимодействия (D-15), гонка при одновременном запуске двух опросов (D-16), нет единой обработки ошибок и студент видит английские технические строки (D-17), студент не видит потери связи (D-19), офлайн-предзагрузка дека не работает (D-20), голос в опросе можно переписать после перезагрузки (D-22), нет ни одного теста на `live`, `feedback`, `qa` и `interaction` (D-23).
