# Готовность к сдаче: расхождения по упаковке

Дата проверки: 18.09.2026. Ветка `v2/phase-5-web-student-channel`.
Проверка только читающая — в проекте ничего не менялось, история не переписывалась.

Важно: во время проверки репозиторий продолжали править. Начата она была на `b399ca6`,
закончена на `319af2d` (за это время добрались B-04, B-05 и вход по MAX `initData`,
а `docs/hackathon/` попала в git). Все факты ниже перепроверены на `319af2d`;
там, где выводы изменились по ходу, это отмечено явно.

Требования взяты из задания хакатона и продублированы в
[ROADMAP.md](../ROADMAP.md) (этап 3) и
[TEAM_TASKS.md](../TEAM_TASKS.md#чек-лист-сдачи) (задачи B-11 … B-15).

## 1. Резюме

Инфраструктурный каркас есть: три Dockerfile, пять compose-файлов, `.dockerignore`,
`.env.example`, CI с проверкой сборки образов. Секретов в рабочем дереве и в истории
git не найдено. OpenAPI покрывает 86 из 87 реальных эндпоинтов.

Блокирующих расхождений пять:

1. `docker compose up` не поднимает адаптеры каналов — у них нет ни Dockerfile, ни
   сервиса в compose, а MAX-адаптера (B-01) не существует вовсе. Требование «все
   локальные компоненты продукта, включая адаптеры каналов» не выполняется.
2. README не закрывает ни один из двенадцати обязательных разделов целиком: из
   32 строк половина — это «быстрый старт фазы 0».
3. Нет тестовых учётных записей по ролям и нет тестовых данных: проверяющий после
   `docker compose up` попадает на пустую базу и упирается в invitation-flow.
4. Нет `DATA-API.yaml` по схеме организаторов (B-12).
5. Сборка не укладывается в 5 минут и превышает норматив кратно. Замер при прогретых
   базовых образах: конвертер — **31 мин 27 с**, ядро — **7 мин 50 с**, веб — около
   минуты. Полная сборка одной командой определяется конвертером: **≈ 31,5 мин против
   норматива 5 мин**. Причина — `apt-get install libreoffice` без фиксации версий
   (206 пакетов, 153 МБ, образ 991 МБ) и отсутствие слоя прогрева Maven. Подробности —
   в разделе 6.

### 2.4 Переменные окружения: расхождения

Переменные, которые читает `core/src/main/resources/application.yml`, но которых нет
в `.env.example`:

`APP_VERSION`, `SERVER_PORT`, `SLIDE_IMAGE_URL_SECRET`, `SLIDE_IMAGE_URL_TTL`,

и ни одним сервисом — мёртвая запись, помечена комментарием как задел на будущее.

Переменные конвертера (`CONVERTER_MAX_SLIDES`, `CONVERTER_BASE_DPI`,
`CONVERTER_OFFICE_TIMEOUT_SECONDS` и ещё девять, `deploy/converter/server.py:12-25`)

| 354,0 → 435,0 с | `jar` | 81 с |
| 435,0 → 468,1 с | `spring-boot:repackage` | 33 с |

Всего за стадию скачано 508 артефактов, 108,5 МБ. Последняя загрузка из Maven Central
происходит на 468,0 с — то есть сеть нагружена вплоть до самого конца стадии.
Чистого счёта (компиляция, сборка jar, repackage) здесь порядка 20–40 с; всё
остальное — ожидание сети.

Разбивка сборки конвертера — это худший результат из трёх образов:

| Стадия | Время |
|---|---|
| `RUN apt-get update && apt-get install -y --no-install-recommends libreoffice poppler-utils fonts-dejavu && rm -rf /var/lib/apt/lists/*` | **1871,5 с** |
| экспорт слоёв | 14,8 с |
| остальное (`COPY server.py`, метаданные) | < 1 с |

Одна строка Dockerfile ставит **206 пакетов, 153 МБ загрузки**, и раздувает образ до
**991 МБ**. Базовый образ при этом уже был в кэше, то есть все 1871,5 с целиком
засчитываются в норматив.

### 6.3 Главный вывод

**Требование «сборка не дольше 5 минут без учёта загрузки базовых образов» не
выполняется, и его выполнение целиком зависит от скорости канала.**

Причина не в объёме кода, а в устройстве Dockerfile:

1. `core/Dockerfile:3-6` копирует `core/src` в один слой с `pom.xml` и сразу запускает
   `mvn package`. Отдельного слоя прогрева зависимостей нет, `~/.m2` наружу не
   вынесен, BuildKit cache mount не используется. Любое изменение исходника
   инвалидирует слой, и все 108,5 МБ зависимостей качаются заново.
2. Тестовые зависимости (testcontainers, docker-java, byte-buddy, archunit) скачиваются
   даже при `-DskipTests` — это ещё около 40 МБ на каждой сборке.
3. `deploy/converter/Dockerfile:3-8` делает `apt-get update && apt-get install libreoffice`
   без фиксации версий: 206 пакетов, 153 МБ, 1871,5 с на прогретом базовом образе.
   Это **главный виновник** — конвертер один превышает норматив в шесть раз, и время
   стадии к тому же плавает вслед за состоянием зеркал Debian.

Порядок величин: конвертер 31,5 мин, ядро 7,8 мин, веб около 1 мин. Норматив 5 минут
не выдерживает ни один из двух тяжёлых образов.

На быстром канале (скажем, 20 МБ/с) 108,5 МБ Maven и 153 МБ apt скачались бы за
секунды, и сборка уложилась бы в норматив. На канале проверяющего это не гарантировано
ничем. Судить о соответствии требованию по одному замеру на быстрой сети нельзя —
зависимость от сети надо убрать из сборки, а не надеяться на неё.

### 6.4 Что нужно, чтобы уложиться в 5 минут гарантированно

| Мера | Эффект | Оценка |
|---|---|---|
| Отдельный слой прогрева Maven: `COPY pom.xml core/pom.xml`, затем `RUN mvn -B -pl core -am dependency:go-offline`, и только после этого `COPY core/src` | Зависимости кэшируются в слое и не перекачиваются при изменении исходников. Повторная сборка сводится к компиляции: 20–40 с вместо 468 с | 1,5 ч |
| Либо BuildKit cache mount: `RUN --mount=type=cache,target=/root/.m2 mvn …` | То же, плюс кэш переживает изменение `pom.xml`. Требует включённого BuildKit у проверяющего | 1 ч (как альтернатива, не дополнительно) |
| Исключить test-scope зависимости из образа (`-Dmaven.test.skip=true` вместо `-DskipTests`, либо отдельный профиль сборки) | Минус ~40 МБ скачивания на каждой холодной сборке | 0,5 ч |
| **Конвертер — приоритет номер один.** Заменить метапакет `libreoffice` на `libreoffice-impress` + `libreoffice-core` (конвертер работает только с презентациями и PDF), зафиксировать версии пакетов, либо взять готовый образ с предустановленным LibreOffice и не собирать его самим | Сейчас одна эта стадия — 1871,5 с из 1887 с. Метапакет тянет Writer, Calc, Base, Java-стек. Урезание до Impress убирает бо́льшую часть из 206 пакетов и 153 МБ | 3 ч |
| Опубликовать собранный образ конвертера в реестр и тянуть его по тегу вместо локальной сборки | Стадия apt уходит из времени сборки совсем и превращается в загрузку базового образа, которая в норматив не входит | 2 ч (как альтернатива, требует доступа к реестру) |
| Кэш `~/.m2` и npm в CI (`actions/setup-java` с `cache: maven` уже есть для шага `mvn verify`, но шаги `docker build` его не видят — нужен `docker/build-push-action` с `cache-from`/`cache-to` типа `gha`) | Сборка образов в CI перестанет качать зависимости заново; появится честный регулярный замер | 2 ч |
| Замер и запись результата в README: `time docker compose build` на чистом клоне при прогретых базовых образах | Закрывает пункт чек-листа «время замерено» | 0,5 ч |

**Итого на приведение сборки к нормативу: около 8 часов** (3 ч конвертер, 1,5 ч слой
прогрева Maven, 0,5 ч test-scope, 2 ч кэш в CI, 0,5 ч замер и запись в README;
альтернативные варианты не суммируются).

Ожидаемый результат после этих мер, при прогретых базовых образах: ядро ≈ 40–60 с,
веб ≈ 65 с параллельно, конвертер — в зависимости от выбранного варианта от нескольких
секунд (готовый образ из реестра) до 3–5 мин (урезанный набор пакетов). То есть в
норматив уложится только вариант с готовым образом конвертера либо с существенно
урезанным apt. **Сейчас требование не выполнено, и без переделки конвертера оно не
выполнится ни на каком канале.**

Отдельно стоит зафиксировать в README, что повторная сборка со слоевым кэшем занимает
1 с: проверяющий, который собирает второй раз, увидит именно это, и разница с первым
прогоном должна быть объяснена, а не выдана за соответствие нормативу.
