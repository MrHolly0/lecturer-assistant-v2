# Содержание презентации Lecturer Assistant

Актуально на 25.09.2026 для контрольной ревизии `3c6e9a2` и текущего рабочего дерева; релизный hash ещё не зафиксирован. Это содержание, а не макет слайдов. `PRODUCT_DEVELOPMENT.md` и раздел 4 `ROADMAP.md` остаются источниками принятого плана; здесь он только сокращён для защиты.

Правило формулировок:

- «реализовано» — найдено в текущем коде;
- «проверено» — есть выполненная проверка с указанным источником;
- «проверено владельцем» — эксплуатационный факт от владельца, не независимый автотест;
- «до сдачи» — принято в работу, но ещё не готовая функция;
- «гипотеза» — нет интервью или пилота.

## Слайд 1. Продукт

**Заголовок:** Lecturer Assistant — обратная связь во время очной лекции через MAX

**Содержание:**

- преподаватель показывает презентацию с компьютера;
- студент в MAX видит текущий слайд, отправляет сигнал понимания, вопрос и ответ на короткую проверку;
- преподаватель получает картину по текущему слайду и может изменить объяснение во время занятия.

**Честная формулировка:** основной кодовый сценарий реализован. Вход преподавателя через одноразовый код в живом MAX проверен владельцем; полный студенческий сценарий ещё должен быть оформлен отдельным двухустройственным протоколом.

## Слайд 2. Проблема

**Гипотеза:** в большой аудитории преподавателю трудно вовремя заметить, на каком месте группа потеряла понимание.

- устный вопрос «всё понятно?» не даёт структурированной картины;
- поднятая рука публична и не связывается автоматически со слайдом;
- отдельные формы и сервисы создают ещё одну точку входа.

**Не заявлять:** что проблема подтверждена интервью, что студенты точно будут активнее или что продукт уже повышает успеваемость. Интервью и пилот не проводились.

## Слайд 3. Пользователь

**Сегмент-гипотеза:** преподаватель потоковой лекции младших курсов технического вуза и студенты этой лекции.

**Контекст:**

- преподаватель — компьютер с презентером;
- студент — телефон или веб-MAX;
- проектор — отдельное окно;
- технический прогон на 150 SSE-подключений выполнен; это проверка инфраструктуры, а не доказательство реального размера потока или продуктовой потребности.

## Слайд 4. Что работает сейчас

1. Преподаватель загружает PDF, PPT, PPTX или ODP.
2. Конвертер локально создаёт PNG слайдов и извлекает текст без внешних сервисов обработки.
3. Преподаватель запускает лекцию.
4. Студент подключается по коду или через MAX.
5. Слайд обновляется по SSE.
6. Сигнал сохраняется для конкретного студента и слайда.
7. Вопрос появляется у преподавателя.
8. В быстром опросе первый ответ фиксируется; распределение и правильный вариант открываются после закрытия.

Seed создаёт тестовый курс, лекцию, презентацию, два вопроса банка и роли admin/lecturer/assistant. Пароли передаются отдельно.

## Слайд 5. Роль MAX

**Реализовано кодом:**

- MAX Bridge: `initData`, `start_param`, тема, viewport и BackButton;
- серверная HMAC-проверка подписи и возраста `auth_date`;
- повторное использование личности по MAX `user.id`;
- одноразовый код привязки роли преподавателя;
- `/start`, `bot_started`, `open_app`, long polling и webhook в отдельном адаптере;
- webhook на постоянном Tuna-стенде.

**Проверено владельцем:** преподаватель вошёл через одноразовый код в живом MAX.

**Ещё требуется:** отдельный протокол студента — вход по ссылке, текущий слайд, сигнал, вопрос, открытый и закрытый опрос, завершение. Проверка преподавателя не доказывает этот путь.

## Слайд 6. Архитектура и надёжность

**Схема:**

`MAX/браузер → Tuna HTTPS → Caddy :18088 → nginx/React → Spring Boot core → PostgreSQL`

`core → Python converter → LibreOffice/Poppler → PNG и текст`

`MAX Bot API ↔ max-adapter ↔ Channel SPI core`

**Факты:**

- Java 21, Spring Boot 3.5.15, React 18, TypeScript, PostgreSQL 16;
- шесть постоянных compose-сервисов;
- постоянный стенд: `https://lecturer-assistant.ru.tuna.am`;
- сторож проверяет стенд каждые 300 секунд, пишет `check.log` и `watch.out`, различает отказ контейнеров и туннеля;
- ежедневный `pg_dump` с хранением по умолчанию 14 дней предусмотрен конфигурацией стенда.

## Слайд 7. Безопасность и данные

**Реализовано:**

- BCrypt для паролей;
- HMAC-SHA256 для JWT и MAX `initData`;
- refresh token и токен анонимного участника хранятся как хеши;
- подписанные временные URL слайдов;
- секретный заголовок и скрытый путь webhook;
- ограниченные CORS и WebSocket origins;
- rate limit для MAX-входа и сигналов;
- изоляция курсов на уровне прикладных проверок.

**Данные:** локальные аккаунты и роли, MAX `user.id` и отображаемый профиль, презентации и извлечённый текст, участие, сигналы, вопросы и ответы.

**Ограничения:** автоматическая политика удаления персональных данных и шифрование данных на диске не утверждены; на стенде используются только тестовые данные.

## Слайд 9. Что вошло до заморозки

Принятый объём реализован в коде и покрыт целевыми тестами:

- итог лекции для преподавателя: участники, проблемные слайды, результаты проверок и число неотвеченных вопросов;
- запуск подготовленного вопроса из банка прямо во время лекции;
- недостающие события для метрик;
- проверенные SQL-выгрузки по методике пилота.

API и frontend слиты; 27 целевых интеграционных тестов и production-сборка web прошли 25.09. Ручная двухустройственная проверка этих функций остаётся частью отдельного MAX-протокола.

## Слайд 10. Дальнейшее развитие

После сдачи:

- история прошлых лекций;
- персональный конспект студента;

Это направления развития, не скрытые функции текущего решения. Подробный план уже принят в `PRODUCT_DEVELOPMENT.md` и `ROADMAP.md`.

## Слайд 11. План пилота

**Статус:** пилота не было.

1. Интервью с преподавателем и проверка сценария.
2. Одна базовая лекция без продукта.
3. Две–три лекции той же группы с продуктом.
4. Технический журнал и короткое интервью после каждой лекции.

**Метрики:**

- доля подключившихся и отправивших сигнал;
- время реакции на рост «Не понимаю»;
- доля ответивших и правильных ответов;
- p95 доставки слайда;
- доля лекций без технического сбоя;
- готовность преподавателя продолжить использование.

Две–три лекции проверяют проходимость и предварительный сигнал пользы, но не доказывают рост успеваемости.

## Слайд 12. Что остаётся гипотезой

- проблема достаточно частая и болезненная;
- студенты охотнее отправляют приватный сигнал, чем задают вопрос вслух;
- преподаватель успевает реагировать во время объяснения;
- вход через MAX повышает долю подключившихся;
- итог лекции и конспект будут востребованы;
- продукт улучшает понимание материала.

Для этих тезисов нельзя использовать слово «подтверждено».

## Служебный блок для команды сдачи

До экспорта финальной презентации владелец подтверждает:

- точное время дедлайна и поля формы;
- URL репозитория, стенда, бота/мини-приложения, OpenAPI и видео;
- публичные тестовые логины;
- дату и устройство проверки преподавательского входа;
- ссылку на полный студенческий протокол.

Пароли, токен бота, `initData`, cookies и секреты окружения в презентацию не попадают.
