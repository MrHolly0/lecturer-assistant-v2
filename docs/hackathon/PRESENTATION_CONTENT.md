# Содержание презентации Lecturer Assistant

Функциональные доказательства собраны 25–27.09.2026; пользователь провёл парный прогон студента и преподавателя в MAX. Модель пилота и граница изоляции уточнены 27.09.2026. Релизная ветка опубликована на GitHub и развёрнута на публичном стенде; на обновлённом стенде 8/8 API-проверок прошли. Полный hash для первого слайда техлид передаёт после финальной фиксации документов. Репозиторий: https://github.com/MrHolly0/lecturer-assistant-v2, ветка `release/hackathon-max`. Это содержание, а не макет слайдов. `PRODUCT_DEVELOPMENT.md` и раздел 4 `ROADMAP.md` остаются источниками принятого плана; здесь он только сокращён для защиты.

Правило формулировок:

- «реализовано» — найдено в текущем коде;
- «проверено» — есть выполненная проверка с указанным источником;
- «проверено владельцем» — эксплуатационный факт от владельца, не независимый автотест;
- «до сдачи» — принято в работу, но ещё не готовая функция;
- «гипотеза» — нет интервью или пилота.

## Слайд 1. Служебная информация для проверки

Обязательный первый слайд по заданию трека; он не оценивается как продуктовая презентация. В репозитории оставляем только шаблон без действующих секретов. В PDF, который команда передаёт организаторам для проверки, заполнить:

- ссылку на работающего бота/мини-приложение MAX;
- ссылку на репозиторий и полный commit hash зафиксированной версии;
- HTTPS-адрес собственного API;
- тестовые логины и пароли для необходимых ролей;
- рабочие токены, API-ключи и значения окружения, **если они необходимы для запуска или проверки**;
- короткую последовательность: вход преподавателя → запуск лекции → вход студента через MAX → сигнал/вопрос/опрос → завершение.

Не публиковать PDF с действующими доступами в открытом репозитории или по общедоступной ссылке. Если нужна публичная версия, подготовить отдельную копию с удалёнными секретами. `initData`, cookies и рабочие пользовательские токены сессии на слайде не нужны.

## Слайд 2. Продукт

**Заголовок:** Lecturer Assistant — обратная связь во время очной лекции через MAX

**Содержание:**

- преподаватель показывает презентацию с компьютера;
- студент в MAX видит текущий слайд, отправляет сигнал понимания, вопрос и ответ на короткую проверку;
- преподаватель получает картину по текущему слайду и может изменить объяснение во время занятия.

**Честная формулировка:** основной кодовый сценарий реализован. Вход преподавателя через одноразовый код и действия студентки в живом MAX проверялись владельцем и подругой; после исправления повторного входа и дубля личности владелец сообщил, что работает. Формальный протокол всего пути с датой и ревизией ещё не заполнен.

## Слайд 3. Проблема

**Гипотеза:** в большой аудитории преподавателю трудно вовремя заметить, на каком месте группа потеряла понимание.

- устный вопрос «всё понятно?» не даёт структурированной картины;
- поднятая рука публична и не связывается автоматически со слайдом;
- отдельные формы и сервисы создают ещё одну точку входа.

**Не заявлять:** что проблема подтверждена интервью, что студенты точно будут активнее или что продукт уже повышает успеваемость. Интервью и пилот не проводились.

## Слайд 4. Пользователь

**Сегмент-гипотеза:** преподаватель потоковой лекции младших курсов технического вуза и студенты этой лекции.

**Контекст:**

- преподаватель — компьютер с презентером;
- студент — телефон или веб-MAX;
- проектор — отдельное окно;
- технический прогон на 150 SSE-подключений выполнен; отдельно изолированное ядро прошло 10×150, но полный путь через локальный Caddy не подтвердил этот масштаб. Это проверки инфраструктуры, а не доказательство продуктовой потребности.

## Слайд 5. Что работает сейчас

1. Преподаватель загружает PDF, PPT, PPTX или ODP.
2. Конвертер локально создаёт PNG слайдов и извлекает текст без внешних сервисов обработки.
3. Преподаватель запускает лекцию.
4. Студент подключается по коду или через MAX.
5. Слайд обновляется по SSE.
6. Сигнал сохраняется для конкретного студента и слайда.
7. Вопрос появляется у преподавателя.
8. В быстром опросе первый ответ фиксируется; распределение и правильный вариант открываются после закрытия.
9. Пауза блокирует действия обеих сторон и исключается из активной длительности.
10. После завершения закрывается проектор и доступен итог и история лекции.
11. Лекцию можно быстро запустить с карточки курса; порядок слайдов можно менять, слайды — удалять с сохранением snapshot начатой сессии.
12. Преподаватель видит агрегаты по курсу, группам и постоянным студентам.
13. В MAX преподавателю доступен телефонный пульт текущей лекции со сменой слайдов, паузой, вопросами, проверками и завершением; для иллюстрации нужен реальный кадр и подтверждение на финальной ревизии.

Seed создаёт тестовый курс, лекцию, презентацию, два вопроса банка и роли admin/lecturer/assistant. Нужные жюри тестовые пароли указываются только на служебном слайде закрыто передаваемого PDF.

## Слайд 6. Роль MAX

**Реализовано кодом:**

- MAX Bridge: `initData`, `start_param`, тема, viewport и BackButton;
- серверная HMAC-проверка подписи и возраста `auth_date`;
- повторное использование личности по MAX `user.id`;
- одноразовый код привязки роли преподавателя;
- `/start`, `bot_started`, `open_app`, long polling и webhook в отдельном адаптере;
- webhook на постоянном Tuna-стенде.

**Проверено владельцем:** преподаватель вошёл через одноразовый код в живом MAX.

**Ещё требуется:** оформить уже проведённый парный тест студента по шагам: вход, текущий слайд, сигнал, вопрос, проверка, пауза, завершение, повторное открытие мини-приложения; указать дату, ревизию и доказательства. Не переносить результат одного шага на весь сценарий.

## Слайд 7. Архитектура и надёжность

**Схема:**

`MAX/браузер → Tuna HTTPS → Caddy :18088 → nginx/React → Spring Boot core → PostgreSQL`

`core → Python converter → LibreOffice/Poppler → PNG и текст`

`MAX Bot API ↔ max-adapter ↔ Channel SPI core`

**Факты:**

- Java 21, Spring Boot 3.5.15, React 18, TypeScript, PostgreSQL 16;
- пять основных сервисов (`postgres`, `converter`, `core`, `web`, `max-adapter`); на стенде дополнительно работают Caddy и сервис резервных копий;
- постоянный стенд: `https://lecturer-assistant.ru.tuna.am`;
- сторож проверяет стенд каждые 300 секунд, пишет `check.log` и `watch.out`, различает отказ контейнеров и туннеля;
- ежедневный `pg_dump` с хранением по умолчанию 14 дней предусмотрен конфигурацией стенда.

## Слайд 8. Безопасность и данные

**Реализовано:**

- BCrypt для паролей;
- HMAC-SHA256 для JWT и MAX `initData`;
- refresh token и токен анонимного участника хранятся как хеши;
- подписанные временные URL слайдов;
- секретный заголовок и скрытый путь webhook;
- ограниченные CORS и WebSocket origins;
- rate limit для MAX-входа и сигналов;
- изоляция курсов на уровне прикладных проверок;
- первый администратор создаётся оператором с временным установочным секретом; публичной регистрации администратора нет.

**Данные:** локальные аккаунты и роли, MAX `user.id` и отображаемый профиль, группы, презентации и извлечённый текст, участие, сигналы, вопросы и ответы.

**Ограничения:** автоматическая политика удаления персональных данных и шифрование данных на диске не утверждены; на стенде используются только тестовые данные. Для прошлых лекций группа берётся из текущего состава; временные гости не становятся постоянными профилями. Детекции списывания нет. Изоляция курсов внутри установки не равна изоляции вузов: администратор сейчас видит всю установку.

## Слайд 10. Что вошло до заморозки

Принятый объём реализован в коде и покрыт целевыми тестами:

- итог лекции для преподавателя: участники, проблемные слайды, результаты проверок и число неотвеченных вопросов;
- история завершённых лекций и закрытых проверок;
- запуск подготовленного вопроса из банка прямо во время лекции;
- реальная пауза, активное время и закрытие проектора;
- быстрый запуск лекции с карточки курса;
- изменение порядка и удаление слайдов с COW и snapshot начатой сессии;
- группы, приглашения и аналитика по группам/студентам;
- недостающие события для метрик;
- проверенные SQL-выгрузки по методике пилота.

API и frontend слиты; 131 backend-тест прошёл 27.09, 16 тестов MAX-адаптера и локальная визуальная QA — на предыдущем gate; web lint/build прошли 27.09. Ручная двухустройственная проверка остаётся открытой.

## Слайд 11. Дальнейшее развитие

**Первый пилот:** один вуз и отдельная управляемая установка с собственной базой, файлами и администратором. Оператор создаёт его локальной установочной командой; доступ к MAX настраивается по правилам платформы.

**Масштабирование:** следующие учреждения получают такие же отдельные установки. Общий сервис для нескольких вузов — отдельный этап после реализации и проверки изоляции пользователей, прав администратора, курсов, групп, файлов, аналитики и резервных копий. Текущий код не является мультиарендным сервисом.

Далее после сдачи:

- персональный конспект студента;
- расширение телефонного пульта преподавателя после пилота; базовый пульт уже реализован;
- исторический snapshot состава групп;
- сравнение дисциплин и семестров;
- интеграция с LMS и расписанием.

Это направления развития, не скрытые функции текущего решения. Подробный план уже принят в `PRODUCT_DEVELOPMENT.md` и `ROADMAP.md`.

**Ответ на вопрос жюри о масштабировании:** «Сейчас мы проверяем решение в одном вузе на отдельной установке. Для следующего вуза можем развернуть ещё одну такую же установку. Единый сервис возможен после внедрения изоляции учреждений; мы не заявляем её в текущем прототипе».

## Слайд 12. План пилота

**Статус:** пилота не было.

1. Найти один вуз и ответственного администратора отдельной установки; провести интервью с преподавателем и проверить сценарий.
2. Одна базовая лекция без продукта.
3. Две–три лекции той же группы с продуктом.
4. Технический журнал и короткое интервью после каждой лекции.

**Метрики:**

- доля подключившихся и отправивших сигнал;
- время реакции на рост «Не понимаю»;
- доля ответивших и правильных ответов;
- p95 доставки слайда;
- доля лекций без технического сбоя;
- готовность преподавателя продолжить использование.

Две–три лекции проверяют проходимость и предварительный сигнал пользы, но не доказывают рост успеваемости.

## Слайд 13. Что остаётся гипотезой

- проблема достаточно частая и болезненная;
- студенты охотнее отправляют приватный сигнал, чем задают вопрос вслух;
- преподаватель успевает реагировать во время объяснения;
- вход через MAX повышает долю подключившихся;
- итог лекции и персональный конспект будут востребованы;
- продукт улучшает понимание материала.

Не заявлять детекцию списывания: продукт показывает наблюдаемые взаимодействия, но не определяет нечестное поведение по косвенным сигналам.

Для этих тезисов нельзя использовать слово «подтверждено».
