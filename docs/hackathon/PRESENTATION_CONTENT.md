# Содержание презентации Lecturer Assistant

Актуально для ревизии `bb4386a` от 24.09.2026. Это содержание, а не макет: команда самостоятельно выбирает визуальное оформление и сокращает текст под регламент выступления.

Правило формулировок:

- «реализовано», «проверено кодом» — только для функций и свойств, найденных в текущей ревизии;
- «тесты прошли» — только для фактически выполненных команд, перечисленных в разделе «Фактическая база»;
- «предполагаем», «гипотеза», «планируем проверить» — для проблемы, поведения пользователей и продуктовой ценности;
- «подтверждено пользователями» не использовать: интервью с преподавателями и студентами не проводились, пилота не было.

## Слайд 1. Продукт и сценарий

**Заголовок:** Lecturer Assistant — обратная связь во время очной лекции через MAX

**Основное содержание:**

- преподаватель показывает презентацию и ведёт лекцию с компьютера;
- студент открывает мини-приложение MAX, видит текущий слайд, отправляет сигнал понимания, вопрос или ответ на короткий опрос;
- преподаватель видит агрегат по текущему слайду и может сразу проверить повторное объяснение.

**Статус:** функции подтверждены кодом. Полный сценарий с живым ботом и текущим ngrok-стендом ещё не зафиксирован ручным прогоном.

## Слайд 2. Проблема

**Заголовок:** Преподавателю может быть трудно заметить потерю понимания в большой аудитории

**Основное содержание:**

- устный вопрос «всё понятно?» не даёт структурированной картины по группе;
- вопросы и сигналы во время лекции не связываются автоматически с конкретным слайдом;
- отдельный сервис опросов добавляет ещё одну точку входа для студента.

**Обязательная оговорка:** это продуктовая гипотеза команды, а не результат исследования. Неизвестны частота проблемы, готовность преподавателя следить за дополнительной панелью и готовность студентов отправлять сигналы.

## Слайд 3. Пользователь

**Целевой сегмент-гипотеза:** преподаватель потоковой лекции младших курсов технического вуза и студенты этой лекции.

**Контекст использования:**

- преподаватель работает в веб-презентере;
- студент использует телефон с MAX или веб-MAX;
- типовой размер потока для технической проверки — до 150 одновременных участников, но фактическая потребность сегмента интервью не подтверждена.

**Не заявлять:** что преподаватели уже подтвердили проблему, что студенты предпочитают приватный сигнал или что вход через MAX повышает участие.

## Слайд 4. Решение

**Заголовок:** Один живой экран на протяжении всей лекции

**Последовательность:**

1. Преподаватель загружает PDF, PPT, PPTX или ODP и создаёт лекцию.
2. Система локально конвертирует презентацию в слайды и извлекает текст без внешних сервисов обработки.
3. Преподаватель запускает сессию и показывает код или MAX-ссылку.
4. Студент подключается и получает текущий слайд через SSE.
5. Сигнал `Понятно / Есть вопрос / Не понимаю` сохраняется для конкретного слайда.
6. Вопрос студента появляется у преподавателя.
7. В коротком опросе первый ответ фиксируется; распределение и правильный ответ открываются студенту только после закрытия.

**Факт:** frontend текущей ревизии обрабатывает открытый и закрытый опрос, собственный ответ и потерю SSE-соединения; production-сборка проходит.

## Слайд 5. Роль MAX

**Подтверждено кодом:**

- MAX Bridge передаёт `initData`, `start_param`, тему, viewport и состояние BackButton;
- backend проверяет подпись `initData` и возраст `auth_date`, затем выдаёт обычный JWT;
- повторный вход одного `user.id` MAX использует того же человека;
- бот обрабатывает `/start` и `bot_started`, отправляет кнопку `open_app` с кодом лекции;
- адаптер поддерживает long polling и webhook, входит в compose и читает Channel SPI outbox;
- экран подключения строит MAX-ссылку и QR-код, если при web-сборке задан `VITE_MAX_BOT_NAME`.

**Операционное состояние, не результат теста продукта:** бот выдан организаторами; по данным владельца отдельная модерация не требуется. Токен присутствует в локальной `.env`, но имя бота, ссылка мини-приложения и успешный live-прогон ещё не зафиксированы в открытых материалах.

**Не завершено:** привязка MAX-аккаунта преподавателя; итоговые сообщения после лекции не создаются в outbox.

## Слайд 6. Архитектура

**Схема для переноса в графику:**

`браузер преподавателя → nginx/React → Spring Boot core → PostgreSQL`

`MAX или браузер студента → nginx/React → HTTP + SSE → core`

`core → converter → LibreOffice/Poppler → PNG и текст слайдов`

`MAX Bot API ↔ max-adapter ↔ Channel SPI core`

**Ключевые решения:**

- модульный монолит Java 21 / Spring Boot 3.5.15;
- PostgreSQL 16 для метаданных и взаимодействий, Docker volume для файлов;
- React 18 / TypeScript для интерфейсов преподавателя и студента;
- адаптер MAX отделён от core и общается через внутренний API;
- один серверный broadcaster формирует снапшот сессии и рассылает его SSE-клиентам;
- базовый запуск — `docker compose up --build`.

## Слайд 7. Безопасность и данные

**Подтверждено кодом:**

- пароли хешируются BCrypt;
- access token подписывается HMAC-SHA256 и имеет ограниченный срок;
- refresh token и токен анонимного участника хранятся в БД только как хеши;
- MAX `initData` проверяется по HMAC и времени выпуска;
- URL изображений слайдов подписаны и стабильны внутри временного окна;
- webhook MAX проверяет секретный заголовок и скрытый путь;
- проверки изоляции курса не дают использовать идентификаторы сущностей другого курса;
- прод-конфигурация требует секреты, включает TLS через Caddy и ежедневный `pg_dump` с хранением 14 дней.

**Какие данные обрабатываются:** имя и email локального аккаунта, MAX `user.id` и отображаемые поля профиля, материалы лекции, участие в сессии, сигнал по слайду, вопрос и ответ на опрос.

**Честные ограничения:** политика сроков хранения персональных данных не утверждена; шифрование данных на диске не настроено; HTTP CORS явно не настроен, WebSocket допускает любой origin; rate limiting входа и сигналов отсутствует.

## Слайд 8. Текущие ограничения и готовность

**Реализовано и проверено:**

- compose-конфигурация валидна и включает core, web, PostgreSQL, конвертер и адаптеры;
- кодовый цикл MAX-auth → участие → сигнал/вопрос/опрос покрыт выбранными интеграционными тестами;
- frontend текущей ревизии собирается для production;
- холодная сборка по замеру 24.09 укладывается в норматив пяти минут при указанных условиях.

**До отправки обязательно:**

- зафиксировать актуальный ngrok-адрес непосредственно перед сдачей; адрес меняется после перезапуска;
- указать реальное имя бота и встроить `VITE_MAX_BOT_NAME` в финальную web-сборку;
- подготовить тестовые логины, курс, презентацию и лекцию;
- завершить или исключить из сценария привязку MAX к преподавателю;
- пройти сценарий жюри на двух устройствах и сохранить результат;
- выполнить и задокументировать k6-прогон на 150 участниках.

## Слайд 9. План пилота

**Статус:** это план будущей проверки, пилот ещё не проводился.

**Предлагаемый дизайн:**

1. Одна базовая лекция без продукта.
2. Две–три лекции той же группы и преподавателя с Lecturer Assistant.
3. Перед пилотом — интервью и короткая репетиция сценария.
4. После каждой лекции — технический журнал и короткое интервью преподавателя.

**Метрики:**

- доля вошедших и время до первого слайда;
- доля студентов, отправивших сигнал или вопрос;
- время реакции преподавателя на рост `Не понимаю`;
- доля ответивших и доля правильных ответов в вопросе-проверке;
- p95 задержки от смены слайда до показа у студента;
- доля лекций без технического сбоя;
- готовность преподавателя продолжить использование и причины ответа.

**Ограничение вывода:** две–три лекции не доказывают рост успеваемости. Такой пилот проверяет проходимость сценария, удобство и предварительный сигнал пользы.

## Слайд 10. Вывод

**Допустимая формулировка:**

> Мы собрали прототип живой обратной связи для очной лекции с входом через MAX. Кодовый сценарий реализован и покрыт целевыми тестами; до сдачи мы подтверждаем его на живом боте и двух устройствах. Продуктовую востребованность проверим интервью и пилотом — сейчас это гипотеза, а не доказанный эффект.

### Зафиксированный замер сборки

Источник — `deploy/BUILD_TIME.md`, замер 24.09.2026:

- `core + converter + max-adapter + telegram-adapter`: 57 секунд;
- web отдельно: 22 секунды;
- все образы последовательно: около 1 минуты 20 секунд;
- базовые образы были прогреты, build-кэш очищен, сеть работала без зафиксированного замедления;
- web в исходном замере собирался на более раннем коммите, поэтому перед сдачей нужен холодный замер финальной ревизии.

Старый замер 7 минут 50 секунд из `research/PACKAGING_GAPS.md` описывает Dockerfile до оптимизации и не должен подаваться как текущее состояние.

### Нагрузочный прогон

Подтверждено только наличие сценария `e2e/k6/student-sse.js`:

- разгон до 150 SSE-клиентов;
- удержание 150 клиентов три минуты;
- пороги `p95 < 2 с`, успешное открытие SSE и checks > 99%;
- вход анонимного участника, получение SSE и отправка сигнала.

В репозитории нет сохранённого отчёта k6, команды с реальным join-кодом, commit hash стенда и фактических значений p95. Поэтому нельзя писать «нагрузочный тест пройден» или «150 студентов подтверждены». Корректно: «нагрузочный сценарий подготовлен; контрольный прогон запланирован до отправки».

## Что остаётся гипотезой

- проблема достаточно частая и болезненная для преподавателя;
- студенты охотнее отправляют приватный сигнал, чем задают вопрос вслух;
- преподаватель успевает реагировать на панель во время объяснения;
- вход через MAX повышает долю подключившихся;
- связь сигнала со слайдом полезна преподавателю;
- предложенный итог после лекции нужен пользователям;
- решение улучшает понимание материала или успеваемость.

Для этих утверждений нет интервью и результатов пилота. В презентации использовать слова «предполагаем», «планируем проверить» и «метрика пилота».
