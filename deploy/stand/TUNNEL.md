# Временный стенд за туннелем

Пока нет VPS, стенд работает на машине владельца за туннелем. Схема та же, что на VPS:
prod-оверлей с обязательными секретами и Caddy, разводящий маршруты. Отличие одно:
HTTPS снаружи обеспечивает туннель, а Caddy слушает HTTP на `127.0.0.1:18088`
(`TUNNEL_PORT`).

**Текущий адрес: https://lecturer-assistant.ru.tuna.am** (с 24.09.2026).

```
MAX / браузер ──HTTPS──> Tuna ──> Caddy :18088 ─┬─ /webhook/*             → max-adapter:8090
                                                ├─ /api/*, /ws/*, /health → core:8080
                                                └─ остальное              → web:80
```

## Tuna: как устроено и чем рискуем

- Платный тариф Tuna со статичным поддоменом `lecturer-assistant.ru.tuna.am`. Адрес не
  меняется при перезапуске, страницы-предупреждения нет: мобильный браузер и webview
  получают приложение с первой загрузки.
- Туннель держит клиент **Tuna Desktop на машине владельца**. Он должен смотреть на
  `127.0.0.1:18088`. Стенд живёт, пока одновременно выполняются три условия:
  - машина включена и не спит;
  - запущен клиент Tuna;
  - оплачен тариф.
- **Риск для периода оценки 30.09–14.10.** Сон или перезагрузка ноутбука, обрыв сети или
  закрытый клиент — и у жюри стенд недоступен. Для оценки стенд переносится на VPS
  (раздел «Переезд на VPS»); до переезда владелец отключает сон и держит клиент запущенным.

### Замер 24.09: SSE и WebSocket через Tuna

Экран студента получает состояние лекции через SSE, проектор — через WebSocket. Сервер шлёт
снимок SSE раз в секунду. Замер: тестовый преподаватель запускает лекцию, анонимный
студент открывает `/api/v1/student/sessions/{код}/events` через публичный адрес с
мобильным User-Agent. За 80 с преподаватель 7 раз меняет слайд, затем лекция 60 с идёт
без действий.

| | Tuna | Caddy напрямую |
|---|---|---|
| событий | 82 за 81 с | 83 за 82 с |
| интервал между событиями p50 / p95 / max | 1001 / 1014 / 1217 мс | 1000 / 1008 / 1017 мс |
| интервалов < 100 мс (признак буферизации) | 0 | 0 |
| смена слайда дошла | 7 из 7 | 7 из 7 |
| задержка смены слайда мин / медиана / макс | 171 / 511 / 935 мс | 91 / 517 / 950 мс |
| поток за 60 с простоя | не оборвался | не оборвался |

Повтор после B-13 (CORS и лимиты): 85 событий за 84 с, 7 из 7 смен, медиана 726 мс.
Рукопожатие WebSocket `/ws/session/…` со своего origin — 101, с чужого — 403.
Буферизации нет. Задержку до ~1 с задаёт секундный такт сервера, туннель добавляет около
0,1 с. Мобильная сеть и webview MAX этим замером не покрыты.

## Запуск

```bash
sh deploy/stand/init-env.sh      # один раз: секреты в .env, токен бота спросит, если его нет
# в .env стенда: PUBLIC_DOMAIN=lecturer-assistant.ru.tuna.am
sh deploy/stand/tunnel.sh        # весь продукт под PUBLIC_DOMAIN + проверка снаружи
sh deploy/stand/tunnel.sh status # адрес и состояние контейнеров
sh deploy/stand/tunnel.sh stop   # остановить (данные в томах сохраняются)
```

Если `PUBLIC_DOMAIN` пуст, `tunnel.sh` сам поднимает ngrok (см. ниже). Стенд — отдельный
проект compose `lecturer-stand` со своими томами, с локальным `docker compose up` он не
пересекается. Тестовые данные:

```bash
SITE_DOMAIN=lecturer-assistant.ru.tuna.am ACME_EMAIL=unused@example.invalid \
  docker compose -p lecturer-stand -f docker-compose.yml -f docker-compose.prod.yml \
  -f docker-compose.tunnel.yml run --rm -e SEED_PUBLIC_URL=https://lecturer-assistant.ru.tuna.am seed
```

## Сторож и журнал доступности

```bash
sh deploy/stand/watch-install.sh           # проверка каждые 5 минут + не давать Mac засыпать
sh deploy/stand/watch-install.sh status    # что загружено и последние строки журнала
sh deploy/stand/watch-install.sh remove    # снять обе задачи
sh deploy/stand/watch.sh                   # одна проверка вручную
```

`watch.sh` каждые 5 минут: проверяет стенд снаружи (`check.sh`), а если не отвечает —
отличает «упали контейнеры» от «не работает туннель». Контейнеры поднимает сам, но **только
compose-проект `lecturer-stand`**: чужие контейнеры на машине он не трогает. Если стенд жив
локально, а по публичному адресу недоступен, значит не запущен клиент Tuna, нет сети или
закончился тариф; сторож пишет об этом и ничего не перезапускает. Ещё он проверяет, что
последняя копия базы свежее 26 часов.

- **Журнал** `deploy/stand/check.log`: строка с временем на каждую проверку (`OK`,
  `ТРЕВОГА`, `ВОССТАНОВЛЕН`). По нему можно показать, что стенд был доступен весь период
  оценки 30.09–14.10; журнал не в git, его нужно сохранить перед сдачей.
- **Уведомления macOS:** одно на падение и одно на восстановление, а не каждые 5 минут.
- **Сон.** Сторож не разбудит спящий Mac: пока система спит, проверки не выполняются и
  стенд недоступен. Поэтому установщик запускает `caffeinate -i -s`, который не даёт системе
  уснуть при подключённом питании. Это не спасает при закрытой крышке ноутбука без внешнего
  монитора и при работе от батареи: держите Mac включённым в сеть, крышку открытой, а в
  «Экономии энергии» отключите сон.
- Сторож ставится как два файла в `~/Library/LaunchAgents` (`ru.lecturer-assistant.stand-watch`
  и `…stand-awake`), других изменений на системе нет.

## Что меняется при смене адреса

И при смене туннеля, и при переезде на VPS адрес задаётся одной переменной: `PUBLIC_DOMAIN`
для туннеля или `SITE_DOMAIN` для VPS. Всё, что выводится из неё, обновится само после
`tunnel.sh` или `vps-up.sh`.

| Что | Как обновляется |
|---|---|
| `MAX_WEBAPP_URL` (адрес в кнопке `open_app` бота) | автоматически, `https://<адрес>/` |
| `MAX_WEBHOOK_URL` (вебхук бота в MAX) | автоматически: адаптер при старте удаляет прочие подписки бота и регистрирует новую |
| `APP_CORS_ALLOWED_ORIGINS` (CORS и WebSocket, B-13) | автоматически, `https://<адрес>` из prod-оверлея. Вручную задавать не нужно; если задать, значение перекроется |
| **Ссылка мини-приложения в кабинете MAX** | **вручную**: платформа MAX для партнёров → «Чат-боты» → бот → ⋮ → «Настройки» → `https://<адрес>/` |
| Адрес стенда в `README.md` и в сценарии для жюри (`docs/hackathon/JURY_WALKTHROUGH.md`) | вручную, коммитом |
| `servers` в OpenAPI и публичные URL в `DATA-API.yaml` | вручную, коммитом |
| Клиент туннеля (Tuna) | при переезде на VPS — остановить, чтобы старый адрес не отдавал устаревший стенд |
| Ссылки, QR-коды, сообщения команде и жюри | вручную |

Проверка после смены: `sh deploy/stand/check.sh <адрес>` — все строки OK.

## Запасной вариант: ngrok

Бесплатный ngrok проверен 24.09 и для мини-приложения не годится. На запросы с браузерным
`User-Agent` он отвечает страницей «You are about to visit…». Обойти её можно только
заголовком `ngrok-skip-browser-warning`, а webview MAX его на первую загрузку не ставит.
Для проверки бота и вебхука ngrok подходит: серверные запросы MAX доходят. Адрес меняется
при каждом перезапуске, если не задан `NGROK_DOMAIN`.

## Почему не Cloudflare quick tunnel

Проверено 24.09 с машины разработчика (cloudflared 2025.2.1):

- QUIC: `failed to dial to edge with quic: timeout`;
- `--protocol http2`: `TLS handshake with edge error: EOF`;
- выданный адрес `*.trycloudflare.com` отвечает 530.

Кроме того, по документации Cloudflare quick tunnel не поддерживает Server-Sent Events.

## Переезд на VPS

Туннель и VPS используют одни и те же файлы, код не меняется:

```bash
sh deploy/stand/tunnel.sh stop     # на машине владельца; затем закрыть клиент Tuna
sh deploy/stand/vps-up.sh --seed   # на VPS, в клоне репозитория; --seed добавляет тестовые данные
sh deploy/stand/watch-install.sh remove   # на машине владельца: снять сторожа и защиту от сна
```

`vps-up.sh` делает всё остальное:

- спрашивает домен (`SITE_DOMAIN`), почту и токен бота, генерирует секреты;
- поднимает стек с Let's Encrypt;
- проверяет доступность снаружи и ставит эту проверку в cron раз в час.

Дальше — ручные строки из таблицы «Что меняется при смене адреса». Данные тестового стенда
не переносятся: на VPS их создаёт `docker compose run --rm seed`. Если нужна та же база,
перенесите дамп из `deploy/stand/backups/` и восстановите по `deploy/stand/README.md`.
