# CI/CD в GitLab

Пуш в `master` запускает проверки, затем сборку образов и публикацию в Container Registry проекта. Merge request в `master` запускает проверки. Они включают Maven с Testcontainers, тесты и сборку web, тесты MAX и распределённых сервисов с PostgreSQL, проверки установщиков и конфигураций Compose.

## Сборка и тесты

1. Включить Container Registry проекта и создать защищённую ветку `master` с ревью изменений перед слиянием.
2. Подключить Linux runner с Docker executor и тегом `lecturer-ci`. Maven и сборка образов используют отдельный Docker-in-Docker на задание. Для этого нужен выделенный runner с `privileged = true`, без подключения Docker socket хоста. Незащищённые ветки и merge request должны иметь доступ к тестовому runner, если проверки там включены.
3. По умолчанию образы собираются для `linux/amd64`. Для ARM‑сервера задайте `BUILD_PLATFORMS=linux/arm64` на ARM‑runner или настройте эмуляцию на runner сборки. Для обеих архитектур используйте `linux/amd64,linux/arm64`.

Образы помечаются SHA коммита. Для выкладки пайплайн передаёт ссылки на digest из результатов сборки. Для доступа к Registry используются встроенные переменные `CI_REGISTRY_*`.

## Подключение выкладки после выбора сервера

`deploy:production` рассчитан на обычный Compose‑стенд проекта с Caddy, включая режим Tuna. Пакет `deploy/appliance` с внутренним K3s собирается, а обновления такой установки идут через её подписанный каталог.

1. На сервере подготовить Docker, Compose ≥ 2.24.4, `curl`, `jq` и отдельный проектный runner `lecturer-deploy` с shell executor и доступом к локальному Docker. Пометить runner как **Protected**, отключить запуск заданий без тега. В GitLab включить **Prevent outdated deployment jobs**.
2. Создать постоянный каталог, например `/srv/lecturer-assistant`, доступный runner. Положить туда `.env` с правами `0600`, используя [настройку Compose‑стенда](../cloud/README.md). Среди параметров нужны публичный `SITE_DOMAIN`, параметры MAX, `CONVERTER_API_KEY` и существующий абсолютный путь `BACKUP_DESTINATION` к резервному хранилищу. Для готового стенда использовать его действующий `.env`, имя Compose‑проекта и хранилище. При использовании Tuna клиент туннеля настраивается отдельно.
3. Добавить защищённые переменные проекта с областью `production` для настроек сервера. Для `DEPLOY_ENABLED` выбрать область `*`, чтобы условие создания задания видело её до запуска. Включить её после подготовки сервера и runner.

| Переменная | Значение |
| --- | --- |
| `DEPLOY_ENABLED` | `true` включает автоматическую выкладку с защищённой `master`. До выбора сервера оставьте переменную незаданной. |
| `DEPLOY_DIR` | Абсолютный путь к постоянному каталогу с `.env`. |
| `DEPLOY_COMPOSE_PROJECT` | Имя Compose‑проекта. Для существующего стенда укажите его текущее имя, чтобы подключились те же тома. |
| `DEPLOY_MODE` | `domain` по умолчанию или `tunnel` для Tuna и аналогичных туннелей. |

Задание последовательно скачивает образы по digest, создаёт резервную пару БД и файлов для существующего стенда, запускает сервисы и сверяет SHA через публичный `/api/v1/system/info`. Оно сохраняет использованные Compose‑файлы в `DEPLOY_DIR/releases`, а путь к последнему подтверждённому релизу — в `DEPLOY_DIR/current-release`. Активные ревизии нужны для bind mount Caddy и скриптов копирования. Секреты `.env` хранятся на сервере.

Выкладка Compose может кратко прервать активные занятия. Если запуск или публичная проверка не прошли, задание завершится с ошибкой. Возврат после миграции БД выполняется по процедуре восстановления стенда.
