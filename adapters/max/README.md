# MAX Adapter

B-01. Адаптер бота MAX по образцу `adapters/telegram/telegram-adapter.mjs`: core не
импортирует MAX SDK, общение только через Channel SPI (`/internal/v1/channels/max/...`)
и напрямую с MAX Bot API (`https://platform-api2.max.ru`, см.
`docs/hackathon/research/MAX_API_NOTES.md`).

## Запуск (локально, long polling)

```bash
CORE_URL=http://localhost:8080 \
CHANNEL_INTERNAL_API_KEY=phase-4-local-channel-key \
MAX_BOT_TOKEN=... \
MAX_WEBAPP_URL=https://<домен мини-приложения> \
node adapters/max/max-adapter.mjs
```

Документация MAX прямо рекомендует long polling для разработки вместо туннеля
(`MAX_API_NOTES.md` §1.3). Режим включается по умолчанию, если `MAX_WEBHOOK_URL` не задан.

## Запуск (продакшен, вебхук)

Дополнительно к переменным выше:

```bash
MAX_WEBHOOK_URL=https://<домен стенда>/webhook/<sha256(токена)> \
MAX_WEBHOOK_SECRET=... \
MAX_WEBHOOK_PORT=8090 \
node adapters/max/max-adapter.mjs
```

Адаптер сам:
- при старте вызывает `GET /subscriptions`, удаляет чужие подписки (кроме своего URL) и
  регистрирует новую через `POST /subscriptions {url, secret}` (без `update_types` — получаем
  все типы событий);
- поднимает локальный HTTP-сервер на `MAX_WEBHOOK_PORT`, слушает путь
  `/webhook/<sha256(MAX_BOT_TOKEN)>` (можно переопределить `MAX_WEBHOOK_PATH`), сверяет заголовок
  `x-max-bot-api-secret` через `timingSafeEqual`, на несовпадение или чужой путь отвечает 404 —
  так же, как официальный SDK (`MAX_API_NOTES.md` §1.3).

**HTTPS, домен и маршрутизация до этого порта — зона потока упаковки (`BRIEF_PACKAGING.md`,
Caddy/compose). Этот адаптер сам сертификатов не выпускает и наружу не торчит.**

## Переменные окружения

| Переменная | Обязательна | Значение по умолчанию |
|---|---|---|
| `MAX_BOT_TOKEN` | да | — |
| `MAX_WEBAPP_URL` | да | — (URL мини-приложения из кабинета партнёра) |
| `CORE_URL` | нет | `http://localhost:8080` |
| `CHANNEL_INTERNAL_API_KEY` | нет | `phase-4-local-channel-key` |
| `MAX_API_BASE` | нет | `https://platform-api2.max.ru` |
| `MAX_WEBHOOK_URL` | нет (переключает режим) | — |
| `MAX_WEBHOOK_SECRET` | да, если задан `MAX_WEBHOOK_URL` | — |
| `MAX_WEBHOOK_PORT` | нет | `8090` |
| `MAX_WEBHOOK_PATH` | нет | `/webhook/<sha256(MAX_BOT_TOKEN)>` |
| `MAX_RATE_LIMIT_RPS` | нет | `15` |

Этих переменных ещё нет в `.env.example` — их туда добавляет поток упаковки.
`MAX_BOT_TOKEN` там уже есть (используется и ядром для проверки `initData`, см. B-02) —
адаптер переиспользует то же значение.

## Что делает

- **`bot_started`** (клик «Старт» в диалоге бота или диплинк `?start=<код>`) и **`/start`**,
  набранный текстом (`message_created`), — отвечает сообщением с кнопкой `open_app`.
- **Кнопка `open_app`.** MAX_API_NOTES.md §7 оставляет открытым, какая комбинация полей
  `web_app`/`contact_id`/`payload` обязательна и доходит ли `payload` кнопки до мини-приложения
  как `start_param`. Мы не полагаемся на непроверенное: код лекции кладём прямо в URL кнопки —
  `${MAX_WEBAPP_URL}?startapp=<код>` — это задокументированный и однозначный путь (§1.7).
  `payload` тоже передаётся, на случай если он действительно доходит.
- Любой другой текст в диалоге с ботом — короткая подсказка с той же кнопкой открытия
  мини-приложения (без кода), без обращения к core: диалог бота не основной интерфейс,
  им может быть студент, который написал что угодно до входа в мини-приложение.
- Регистрирует возможности канала (`PUT .../capabilities`) и рассылает сообщения из
  `channel.outbox` через `POST /messages`, с глобальным ограничителем частоты
  (`MAX_RATE_LIMIT_RPS`, по умолчанию 15 — с запасом от документированных 30 rps на хост,
  `MAX_API_NOTES.md` §1.2). Outbox пока пуст: сигналы и итоги лекции (B-06, B-08) ещё не пишут
  туда сообщений, поэтому эта часть — задел на будущее, а не то, что видно в демонстрации сейчас.

## Что не проверено на живом MAX

Токен бота в `.env` уже есть, но в этой рабочей среде исходящие HTTPS-запросы на
`platform-api2.max.ru` не проходят (TLS-рукопожатие рвётся ещё на уровне сети — `max.ru`,
`st.max.ru`, `dev.max.ru` при этом открываются). Поэтому:

- **Не проверено вживую:** что `POST /messages` с `open_app`-кнопкой действительно открывает
  мини-приложение по `?startapp=`; точный формат ответа `/messages` (поле id сообщения — код
  предполагает `message.mid` либо `message.id`, схема нигде не приведена целиком); поведение
  при превышении 30 rps (код на всякий случай разбирает `Retry-After`, но это не подтверждено
  документацией); точная схема `message_created.message` (кто отправитель) — обработано
  best-effort с несколькими вариантами поля и молчаливым пропуском, если ни один не подошёл.
- **Проверено юнит- и интеграционными тестами** (`node --test adapters/max/*.test.mjs`, 15/15):
  сборка `open_app`-кнопки и `?startapp=` URL, разбор `/start` и `bot_started`, проверка секрета
  вебхука, рендер клавиатуры для outbox, ограничитель частоты — и сквозной прогон самого адаптера
  отдельным процессом против локальных заглушек core и MAX Bot API (long polling и вебхук).
- Как только появится рабочий HTTPS до `platform-api2.max.ru` (со стенда или из другой сети) —
  первым делом смоктест: `/start` в чате с ботом должен прислать кнопку, которая открывает
  реальное мини-приложение с кодом лекции в адресной строке.

## Чего нет

- Вложений (картинок) в исходящих сообщениях — не нужны боту, слайд показывает мини-приложение.
- Редактирования уже отправленного сообщения — в справке нет подтверждённого API для этого.
- Dockerfile и compose-сервис для этого адаптера — зона потока упаковки (`BRIEF_PACKAGING.md`,
  дефект P-1/P-2 из `research/PACKAGING_GAPS.md`): без него `docker compose up` бота не поднимет.
